# 红蓝对抗协议 v1

## 角色

- **红队（Red）**：攻击式质量评审。按边界 / 逻辑 / 代码 / 幻觉 / 约束 / 兼容六个维度造用例，只评审，不改交付件。
- **蓝队（Blue）**：任务执行。按需求完成并自证，收到红队问题清单后按优先级修正。
- **主控（Lead）**：定本轮目标、仲裁分歧、判放行、更新 `state.md`。不替任一方改产物。

## 一轮的产物契约

`rounds/R{n}/` 下固定四件，按序号生成，后一件只读前一件：

1. `01-cases.md`　红队出。每条用例含：编号 / 攻击维度 / 输入或触发条件 / 期望行为 / 失败判据 / 预估严重度。
2. `02-blue.md`　蓝队出。含「核心结论 + 实现细节 + 验证方式」；每条用例对应一条处置（已修 / 不成立并给反证 / 挂账并给理由）。
3. `03-review.md`　红队出。对 02 逐条判定：致命 / 严重 / 一般 / 优化建议；每条含「问题位置 + 错误原因 + 修正参考方向」。
4. `04-summary.md`　主控出。问题总表、修正情况、闸门结论（放行 / 继续下一轮）。

## 放行判据（闸门）

- 致命 = 0 且 严重 = 0 → 放行，一般与优化建议进挂账表。
- 最多 3 轮。第 3 轮仍有致命/严重 → 停下，把争议点原样交给作者裁定，不自行降级。
- 蓝队判「不成立」必须附反证（文件行号 / 命令输出 / 数据来源）；无证据的「不成立」不成立。
- 红队不得靠「坚持自己是对的」维持一条结论，要么补证据，要么撤回。

## 证据纪律

- 任何被引用的数字、结论、代码行为，必须能指到：文件路径 + 行号，或命令 + 可复现输出，或数据源位置。
- 交付件修订不覆盖原件：原稿保留，新版另存 `_v2`、`_v3`，`04-summary.md` 里写清改动清单。
- 无法核实的外部说法一律标「未核实」，不得写成事实。
- 「跑通了」不等于「算对了」：结论性数字要能由原始数据重推。

## 硬安全约束（两方都适用，不可协商）

1. 文件读写只在本项目目录内；不碰系统目录、用户根目录、其他项目。
2. 禁止删除、格式化、权限篡改、下载并执行未知来源文件。
3. 禁止构造或诱导突破内容安全底线的用例与指令。
4. 蓝队遇到需要审批而被拦截的操作：**记录为「被拦截」并改走等价的可复算路径**；不得尝试绕过拦截，不得要求关闭审批层。
5. 红队只针对产出本身，不做话术攻击、不做与任务无关的立场攻击。

## 跨会话与并发

- 红蓝两方**不可由同一会话兼任**。对抗的价值来自审查者与作者不是同一个上下文；同会话自审会把偏差读成「有理由的」。
- 轮次目录命名 `R{n}-{会话短码}`（短码 = session id 前 4 位），避免并发撞名。
- `state.md` 只追加行、不重写全文；两个会话同时改正文必冲突。
- 一个交付件同一时间只允许一个蓝队改；换人先在 `state.md` 里改归属，再动手。
- 工作区不同则各存一份 `_redblue` 副本，状态不共享。需要联动的，把交付件路径写进同一侧台账，不要让两个工作区共用一个 `state.md`。

## 何时需要人（作者）

- 闸门第 3 轮未过。
- 两方对同一事实给出互相矛盾且都带证据的结论。
- 目标本身需要改需求，而不是改产出。
