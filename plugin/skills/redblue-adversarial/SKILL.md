# 红蓝对抗 v3：单对话自动化

## 0. 用户的底线要求（每次开工先读，不是可选建议）

> 以下是用户 2026-11-02 的原话要求，**是硬约束，不是风格偏好**。红队要拿它审，蓝队要拿它改，主控要拿它判。

**必须实事求是地做，有什么才能做什么。**
不要以预期为导向，而是要有**实打实的基地（地基/证据）和数据报告**来支撑。
可以设想，但**设想和实际矛盾时，重新设想**——不是让数据迁就设想。
总之要**真正像科研一样做任务**。

**明确禁止三件事**：

| 禁止 | 具体表现 | 判定 |
| --- | --- | --- |
| **AI 幻觉** | 编造数字、编造引用、编造"实测过"、把推断写成事实 | 致命 |
| **阿谀奉承** | 报喜不报忧、把"部分成立"说成"完全成立"、把未核实说成已核实 | 致命 |
| **为求快而做少** | 少跑一组对照、少核一个数字、用"看起来合理"代替复算 | 严重 |

**明确鼓励一件事**：

> 「我反倒希望你做得慢一点，做得稳扎稳打一点。」
> 所以**速度不是目标，完整性才是**。少一轮不如多一轮；多花 20 分钟复算，好过省 20 分钟然后被推翻。

**这三条怎么落到红蓝对抗里**（不是口号，是判据）：

1. **每个结论必须有落地证据**：`文件:行号` 或 `命令 + 实际输出`。没有就标「未核实」，**不许写成结论**。
2. **设想与数据冲突时，以数据为准**：`04-summary.md` 必须有「## 设想 vs 实际」小节，写清哪条设想被数据推翻、改成了什么。**设想被推翻不算失败，掩盖推翻才算失败。**
3. **红队专设一列审"证据是否落地"**：`03-review.md` 的判定表里，凡是「证据」列写不出可复算内容的条目，红队有权直接判「不成立」。
4. **不许因为怕被骂而缩小范围**：`00-target.md` 的「未覆盖范围」必须如实列全，**缩小审查范围本身就是一个缺陷**，要被红队审。
5. **阿谀奉承的机械识别**：`gate` 之外的软性检查——凡出现「完全」「彻底」「全面」「毫无疑问」这类词，必须紧跟一个可复算证据；否则红队按「过度声称」处理。

## 1. 一句话

**一个对话跑完全程**：主控 = 主对话，红队 / 蓝队 / 复核全部用 `subagent`（全新上下文）。运行中**不向用户提问**（除 §0 那次交付件确认）。

## 2. 十五条硬规则

1. **用 `subagent`，禁用 `subagent_fork`**。fork 会继承本对话（作者的全部推理），"自己审自己"立刻成立，独立性失效。
2. **主控不得替代红队或蓝队**（v6.24，R10 假放行的根因）。红队两路都没启动、蓝队子代理失控时，**唯一正确的动作是如实记「本轮无红队交付」并进下一轮重跑**，不许自己写 `02-blue.md` 再自己判「全部已消除」。实测后果：`R10-1102a1` 主控代笔蓝队 + 无红队，判 20 条全清并放行，被 R11 红队独立复核推翻为「13 条通过 / 6 条未彻底 / 8 条新发现」——**主控自判不可靠是有实证的，不是假设**。闸门已加 `GATE_UNATTACKED` / `GATE_UNEXECUTED` 两道硬拦。
3. **自动化契约**：不提问、不等待确认、不要求选择。交付件类型自己分派、验收标准从"交付件自身主张"反推、严重度拿不准取严、未放行自动进下一轮。所有判断记进 `04-summary.md` 的「主控决策」表。
4. **唯一停下条件**：触发硬安全约束 → 写 `BLOCKED: safety`，把事实交给用户。
5. **红队不改交付件**。**已升级为强制拦截**（v6.26）：插件 `redblue-write-scope` 在红队子代理创建时装一道 `tools.guard`，红队用 `write`/`edit` 改被审件会在**调用发生前**被拒，只放行写到 `红蓝评审-_redblue/` 产物目录。收尾指纹校验保留作第二道（实测四次校验点 3 次运行零命中，防的是从未发生的风险）。**残留**：`bash`/`pwsh` 是任意命令，解析不出重定向目标，shell 写入仍未拦（红队要跑 `redblue.mjs` 就必须留 shell）。
6. **R1 用例 ≤20 条**，每条必须有可判定的失败判据 + 触发输入。R2 起只复核不重造，用例**只增不改**（原有编号与判据一字不动；允许窄口新增 ≤3 条/轮，须写明"R1 为何漏"）。
7. **闸门**：致命 = 0 且 严重 = 0 **且红队真交付、蓝队真执行** → 放行；否则进下一轮；3 轮未过 → `GATE: BLOCKED`（归档但不得宣称定稿）。
8. **挂账不得含致命/严重**（那类必须"已修"或"不成立+反证"）；挂账 > 5 条只提示不阻断。
9. **严重度按 4 类判据**：论文/报告、数据集/脚本、代码/工程、**协议/规范/流程**。两类都沾边取更严。
10. **能复算就复算**：给命令 + 实际输出片段。不能复算写明原因并标「未核实」。禁止"看起来合理""根据常识"。
11. **确定性部分不靠模型算**：每轮必跑 `node tools/redblue.mjs recount` + `gate` + `contract`；与红队自报不一致时**以脚本为准**并记挂账。`gate` 与 `contract` 现在会交叉验证红队/蓝队产物是否真存在——**两条命令都过才叫放行**。
12. **产物只增不改，禁止整篇重写**（v6.24，压缩正反馈的根治）。实测 13 轮里 `03-review.md` 被整篇 `write` **15 次**（累计 130,577 B，最终文件仅 13 KB），同文件重复写的纯浪费 **346 KB = 全部 write 字节的 57%**，直接导致 **40 次压缩**、摘要从 19.7 KB 涨到 87 KB。规则：`01-cases.md` / `00-target.md` / `03-review.md` 只用 `edit` 追加小节；改旧结论就加「## 修订记录」并注明推翻哪条，**保留原文**。写完文件只报「已写 X，N 行，sha256 前 8 位」，**不在对话里复述内容**。每轮收尾跑 `node tools/redblue.mjs churn <roundsRoot>` 查快照残留（R8 有 `03-review-final/-r1/-r2` 三份、R9 有 `-mapped/-r8map` 两份，都是整篇重写的痕迹）。
13. **10 分钟无人应答 → 自动续跑**（v6.25，用户明确要求）。开工即 `auto arm`，每次推进后 `auto beat`；`auto check` 返回 `1` 就**必须自己继续，禁止回头问用户"要不要继续"**。详见 §3.6。
14. **只有真没办法才找用户，且必须带三份 MD + 一份可复制的提问提示词**（v6.25）。「没办法」的定义是**穷尽过**：红队提过、蓝队改过、确定性工具跑过、下一轮重跑过，仍然过不了。详见 §3.7。**不许把"我觉得用户可能有想法"当成没办法。**
15. **对话备份只增不改**（v6.27，用户 2026-11-02 原话要求：对话内容要备份）。每次压缩/轮次边界，把本对话已有内容备份进 `<产物根>/对话备份/`，文件名从 `1.md` 起顺序递增（下一份 = 现有最大号 + 1）；**已写备份只追加、不改写、不删除、不重排**。同时所有红蓝产物一律路由进 `红蓝评审-_redblue/`，不散落工作区其他目录。

## 3. 流程

### 3.1 开工（主控，不派子代理）

1. 自动定目标：抽交付件自身主张 → 每条一个验收点 → 写 `00-target.md`（**给维度清单，不给红队**）
2. 自动定类型（§5 分派算法）
3. `node tools/redblue.mjs init <roundDir> <交付件...>` —— 建目录 + 基线指纹，一步完成
4. `node tools/redblue.mjs auto arm <roundsRoot> --round=<本轮> --next=<下一步>` —— 上自动续跑的发条
5. 写 `current.json`（可覆写）；`state.md` 暂不写（只在闸门后追加）

### 3.2 R1（三张脸 → 蓝 → 复核 → 主控）

| 步 | 谁 | 输出 |
| --- | --- | --- |
| a1 | **技术审查员** `subagent`：交付件 + 六维度 + 判据表（不给验收标准） | `01-cases-tech.md`（≤12 条） |
| a2 | **领域审稿人** `subagent`：交付件 + 目标期刊/赛事要求 + **文献检索** | `01-cases-domain.md`（≤6 条） |
| a3 | **魔鬼代言人** `subagent`：**只给交付件**，什么都不给 | `01-cases-devil.md`（≤5 条） |
| a4 | 主控：三份合并去重编号 | `01-cases.md` |
| b | 蓝队 `subagent`（新实例） | `02-blue.md` + 交付件新版 |
| c | 技术审查员 `subagent`（新实例） | `03-review.md` |
| d | 主控 | `04-summary.md` + 闸门 + `05-signoff.md`（待签） |

**为什么拆三张脸**：三轮实跑的红队全是技术审查员，抓到的 100% 是局部事实错误，**没有一条**是"这个研究问题不成立"。技术审查员查"写出的对不对"，领域审稿人查"值不值得写"（必须接文献），魔鬼代言人查"根本不该做的理由"（**必须什么都不给**，给维度就等于给框）。

三者可并行，总耗时 ≈ 单个最长者。

**模型：用户划池，机制分配**

用户只决定「今天哪些模型有 token」；机制决定红/蓝/复核各用哪个。

**v6 机制（唯一可用，2026-11-01 实测）**：用 `dsh-subagent-library` 维护一份**具名子代理名册**，一个角色一个 YAML，`provider` / `model` 钉死在文件里。

```
<DSH_HOME>/subagents/
  rb-red.yaml     # 红队：provider=longcat / model=LongCat-2.5-Preview
  rb-blue.yaml    # 蓝队：provider=spark   / model=spark-x2.6
  _backups\
```

主控用 `delegate({ library_id: "rb-red" | "rb-blue", prompt })` 派活。

| 名册 id | 路由 | 定位 |
| --- | --- | --- |
| `rb-red` | longcat / LongCat-2.5-Preview | 红队攻击手 |
| `rb-blue` | spark / spark-x2.6 | 蓝队执行手（**跨厂商，强独立**） |

**换模型（热生效，不用重启、不用新会话）**：改 `rb-red.yaml` 的 `provider:` / `model:` 两行，保存即生效。改前把原文件复制到 `_backups/`。

**可用 provider**：**以 `route probe` 的当次实测为准**（写 `route-cache.json`）。此处不再列硬名单 —— 2026-11-10 实测同一台机器上「profile 已注册」是 4 组、`route` 列出 14 组、用户选择器显示 16 个，三套口径互不相同；**唯一可信的是当次 probe 的快照**，且它有时效（网关按 model 动态路由，同一 (provider,model) 不同时刻可用性可能不同）。

> **不要写 `reasoningEffort`**，除非确认该模型支持该档位。实测 LongCat-2.5-Preview 不支持 `high`，会让子代理在第一个 turn 就以 `UNSUPPORTED_REASONING_EFFORT` 失败。

> **旧方案已废弃**：`rb_lc25` / `rb_lc20` / `longcat_worker` 这三个路由工具当时被认为**从未真正存在于工具面**（profile 层 `insert` 不落到工具面）。
> 
> **⚠ 此结论已于 2026-11-10 被推翻**：profile 配置里 `toolName: longcat_worker` / `rb_lc25` / `rb_lc20` **各出现 1 次**，且 R11–R14 四轮实际就是用 `longcat_worker` 派的（见 §10.17）。
> 保留原文只为记录"曾经的错误认知"，**不是现状**。跨厂商审计（讯飞 Spark）指出它与 §10.17 直接矛盾。

**成本原则（默认，不许破）**：
1. **日常一律 LongCat**，不主动调 DeepSeek 等按 token 计费的模型（白天贵）
2. 跨家族模型只在用户**明确要求**时加进池子，加之前先确认成本
3. 同家族不同尺寸算**弱跨模型**，04 必须写「同家族，独立性收益有限」
4. 跨厂商（LongCat ↔ Spark ↔ DeepSeek）算**强跨模型**，04 记「强独立性」
5. 路由失败降级到**池内**下一条，不自动改用付费模型

**分配**：红队=`rb-red`（LongCat-2.5）；蓝队=`rb-blue`（Spark-x2.6）；领域/魔鬼=与红队不同优先；复核=**与红队同模型但新实例**。只有 1 个名册可用 → 记「独立性受限」。**04 必须逐角色记录实际名册 id 与路由。**
**错误类型**：每条用例必须标 E 码（E01 量纲 / E02 口径 / E03 引用归属 / E04 页码 / E05 统计前提 / E06 逻辑断裂 / E07 覆盖遗漏 / E08 数据可复现 / E09 定义不一致 / E10 结论强于证据 / E11 实现缺陷 / E12 格式合规）。跨项目累积，用来找"我最常犯哪一类"。

**两阶段**：先 3–5 条"该类型最常见的致命点"探测；命中才展开全量，全不中记「探测未命中」收工。

**R2 / R3 是可选**，不是默认流程：最小有效核 = 造 → 修 → **实跑复核**。R2 起 `01-cases.md` 只增不改；`02/03/04` 每轮各一份放当轮目录。

### 3.3 指纹校验（只在收尾做一次）

| 时机 | 判定 |
| --- | --- |
| R1-d 收尾 | `redblue.mjs diff 00-baseline.txt 收尾.txt`；有差异必须与 `02-blue.md` 的"交付件改动"节逐文件对应，否则记"未申报改动"（严重） |

> v3 原本设四个校验点，实测 3 次运行**全部零命中**——"红队改交付件"从未发生；真实发生过的是「迟到的红队覆盖了红队自己的产物」，靠 §2 的"重试写不同文件名"解决。中间三点是纯开销。

### 3.4 收尾闭环（v6，每轮结束必做）

单轮 `gate` 放行只说明**这一轮干净**，不说明**历史声称的修复是真的**。收尾必须跑完三件：

```powershell
# 技能自身位置 = 本 SKILL.md 所在目录的上一级
# 部署后经 junction 也可从 $env:DSH_HOME\skills\redblue-adversarial\..\tools 访问
$f="$env:DSH_HOME\skills\redblue-adversarial\tools\redblue.mjs"
$r='<课题根>\redblue'          # 收尾三件套作用在整个课题的轮次根上
$n='<node.exe 路径>'           # 见 §3.5

# 1) 严重度校准：这一轮的分级有没有失效
& $n $f severity "$r\R4-1101c4\03-review.md"

# 2) 再攻击：上一轮声称修好的，这一轮还站得住吗
& $n $f reattack "$r\R3-1101cf\03-review.md" "$r\R4-1101c4\03-review.md"

### 3.6 自动续跑：10 分钟无人应答就自己往下走（v6.25）

**用户原话**：「当我10分钟没有理他，那他就自行继续下去。」

这条不能靠"主控记得"来实现——R10 已实证主控会自我放行，自觉是最不可靠的一环。所以做成**落盘的确定性状态机**：

```powershell
$f="$env:DSH_HOME\skills\redblue-adversarial\tools\redblue.mjs"
$r='<课题根>\redblue'

& $n $f auto arm   $r --round=R1-1101ab --next='红队两路并行'   # 开工，写 _auto.json
& $n $f auto beat  $r --next='红队已交，派蓝队'                  # 每推进一步就 beat
& $n $f auto check $r                                            # 退出码决定下一步
```

| `auto check` 退出码 | 含义 | 主控必须做什么 |
| --- | --- | --- |
| **0** `AUTO_RUNNING` | 还在超时窗口内 | 继续当前工作，**不打扰用户** |
| **1** `AUTO_CONTINUE` | 已超 600s 无心跳 | **立即自己往下走**：起红队 / 派蓝队 / 进下一轮。**禁止问用户"要不要继续"** |
| **2** `AUTO_DONE` | 已收工（`done=true`） | 停，报结果 |

**为什么用文件不用定时器**：`schedule_create` 的定时器活在宿主进程里，进程一重启就丢；`_auto.json` 落盘，**换一个全新子代理接手也能凭它继续**，不依赖任何对话记忆。这正是"一个对话里跑完"能成立的原因——**记忆在文件里，不在上下文里**。

**收工条件**（写进 `--done`，任一满足即收工）：

- 闸门放行 **且** 收尾三件套（`severity`/`reattack`/`converge`）全绿 → 正常收工
- 连续 3 轮未放行 → `GATE: BLOCKED`，收工但**不得宣称定稿**
- 穷尽后仍需人来判（见 §3.7）→ 收工并交出三份 MD

**每次 `auto beat` 都要更新 `--next`**：这一栏是给"接手的人（或接手的你）"看的唯一线索。写「红队已交，派蓝队」而不是「继续」，后者等于没写。

### 3.7 什么时候才许找用户（v6.25）

**用户原话**：「有什么问题，是可以找我，但我很多都不懂。你先红蓝对抗，直到没有办法，然后再来问我……但更多的是问你自己，你实在毫无办法才来找我。」

所以「找用户」有一道**门**，不是想找就能找：

| 情况 | 能不能找用户 |
| --- | --- |
| 交付件是哪一份不确定 | **不能**——按 §0.1 自动判定；实在不行按"最近改得最多的那份"并写进 `00-target.md` 依据 |
| 严重度拿不准 | **不能**——按 §5 判据，**拿不准取严** |
| 红队和蓝队结论相反 | **不能**——这是正常对抗，记进「未决清单」，按影响排序取前 3 交给人**但不阻断** |
| 某一轮没放行 | **不能**——自动进下一轮 |
| 子代理失败/超时 | **不能**——换通道（`delegate` → headless → 主控直跑），已有实证可行 |
| 工具报错 | **不能**——先读源码、先自检、先造最小复现件 |
| **上述全部穷尽，连续 3 轮同一处卡住，且红队每次都指向同一个"需要外部事实才能判"的点** | **能**——这是唯一合法的门 |

**「没办法」的操作定义**（必须逐条打勾才算穷尽）：

1. 红队至少两路独立提过这个问题（不是同一路反复说）
2. 蓝队试过至少两种修法且都记录在 `02-blue.md`
3. 确定性工具跑过：**实现口径**是「≥2 轮有 `fingerprints/`（每轮跑过 `init`/`fp`）」或「≥2 类留痕（`_auto.json` / `state.md`）」。v6.29M 对齐说明：本行原文点名「`recount`/`gate`/`contract`/`reattack`/`converge` 全跑过」，但实现（v6.25 起）只认指纹与留痕，两者不一致；现按实现口径描述
4. 至少重跑过一轮完整对抗
5. 卡点是**外部事实**（缺数据、缺文献、缺实验条件、需要人来拍板方向），不是"我不确定"

**满足后必须交付三份 MD + 一段提示词**（用户在对话里直接复制，不用开文件）：

```powershell
$f="$env:DSH_HOME\skills\redblue-adversarial\tools\redblue.mjs"
$r='<课题根>\redblue'

& $n $f ask check $r    # 退出码 0=还没穷尽（不许找用户） / 1=可以找用户
& $n $f ask build $r    # 只在 check 通过后才生成，否则 ASK_REFUSED
```

**`ask check` 的五条机械判据**（全过才算穷尽）：

| # | 判据 | 怎么判 |
| --- | --- | --- |
| 1 | 红队两路独立 | 至少 1 轮有 ≥2 份独立 `01-cases*.md`（且不是「继承上一轮」的转抄） |
| 2 | 蓝队 ≥2 种修法 | 至少 1 轮的 `02-blue.md` 记录 ≥2 种处置策略。**同义词都认**：`已修=已处置`、`未修=未处置`、`部分修=部分处置`、`驳回=判不成立`，`挂账` 单列。**实测教训（v6.29M）**：旧判据只认括号里那套文档词，而真实蓝队写的是「已处置/未处置」→ 四对同义词三对认不出，10 轮里 9 轮误判 0 种，`ask` 因此永远到不了「已穷尽」 |
| 3 | 确定性工具跑过 | ≥2 轮有 `fingerprints/`（每轮跑过 `init`/`fp`），或 ≥2 类留痕 |
| 4 | ≥2 轮完整对抗 | 轮次目录 ≥2 |
| 5 | 卡点性质=外部事实 | **须人工在 `_ask/00-gate.md` 写「卡点性质：外部事实 — <具体缺什么>」** |

**第 5 条故意不自动通过。** 前四条能机械查，第五条查不了——"这是不是外部事实"需要判断。所以留痕但不装懂：不写这句话就不许生成求助包。这是本机制里唯一一处**要求人写一行字**的地方，因为它是"找用户"这道门本身。

**三份 MD 的内容**（`ask build` 自动生成，全部从真实产物抽取）：

| 文件 | 内容 | 为什么需要 |
| --- | --- | --- |
| `_ask\01-背景与目标.md` | 交付件是什么、验收点、已跑几轮、五条判据核对结果、**不要重复我们做过的** | 让外部 AI 不必猜上下文 |
| `_ask\02-卡点与已试路径.md` | 未结案条目**附 03-review.md 原始行**、蓝队试过什么、主控复盘、历史轮次表、**明确试过且失败的方向** | 让外部 AI 不重复我们试过的 |

**同时在对话里给出可复制的提问提示词**（`ask build` 会自动打印，直接复制）：

## 4. 闸门

| 条件 | 结论 |
| --- | --- |
| 致命 = 0 且 严重 = 0，**且红队真交付、蓝队真执行** | **放行**（一般/优化进挂账） |
| 仍有致命/严重 | 进下一轮 |
| 第 3 轮仍未放行 | **`GATE: BLOCKED`**，归档但不得宣称定稿 |
| 未修编号集合与上一轮完全相等 | 原地打转 ⇒ 直接 `GATE: BLOCKED` |

- `未修 = 状态 ∈ {未修, 驳回, 部分修}`，按**编号集合**比较。
- **放行必须写三样**：致命/严重 0 的依据、**未覆盖范围**、**挂账清单**。
- **外加「未决清单 + 最需人看的 3 条」**：列红蓝结论不一致的条目，按"若红队判对则影响多大"排序取前 3，写清分歧与双方证据。**不阻断自动化**——但闸门没有外部真值，这是人唯一成本可承受的裁决点。
- **人类签字 `05-signoff.md`（v4）**：闸门放行后生成 05 模板（三条待确认 + 确认/驳回空位 + 签字行）。**没有签字的 05，状态只能写「已放行（待签）」，不许写「定稿」**。签字是异步的——不阻塞下一轮，只阻塞"定稿"这个宣称。**主控禁止替人签**。

### 4.0 闸门的第一道：这一轮真的有人攻击过吗（v6.24）

**这是 2026-11-02 实跑抓到的最大漏洞，必须放在闸门最前面。**

实测 `R10-1102a1`：两路红队（技术审查员、魔鬼代言人）**都没启动**，蓝队子代理失控（`02-blue.md` 全由主控代笔），`03-review.md` 却写「20 条全部已消除」——旧的闸门只看这一张表，于是 `GATE: 放行`。**假放行不是解析错误，是闸门从不问「有人攻击过吗」。**

新闸门的三条硬前提（任一不满足，「全部已消除」不成立，不得放行）：

| 检查 | 判据 | 失败码 |
| --- | --- | --- |
| 红队真交付 | 存在 `01-cases*.md`，其中 ≥1 行「编号 + 级别」判定行（表格态 `\| V01 \| 成立 \| 致命 \|` 或正文态 `### 观点 N` + `- 严重度：致命`）；且**不自述**「本轮无红队交付」 | `GATE_UNATTACKED` |
| 蓝队真执行 | `02-blue.md` 的「逐条处置」小节内 ≥1 行以编号开头的处置行（`C01`/`N1`/`V01`/`观点1（…）`） | `GATE_UNEXECUTED` |
| 表外不入表 | 表外「一般 + 优化」超过容差 3 条 ⇒ 不放行；表外致命/严重 1 条即不放行 | `GATE: 不放行` |

三条的**实际效果**（11 轮真实数据回归）：R8、R11 真放行（exit 0）；R10 假放行被拦；R2（缺红队产物）、R3（表外严重未入表）、R1（表外 4 条超容差）被拦。

### 4.0b 闸门的第二道：结论有没有落地证据（v6.25）

**用户底线「实事求是」在这里变成机械判据，不是口号。**

闸门放行前，`04-summary.md` 必须存在这三节，缺一节即不放行：

| 必需小节 | 判据 | 失败码 |
| --- | --- | --- |
| `## 证据落地` | 本轮每条「已消除」都能指到 `文件:行号` 或 `命令+输出`；标「未核实」的不许算已消除 | `GATE_UNGROUNDED` |
| `## 设想 vs 实际` | 逐条写清哪个设想被数据推翻、改成了什么；**没有小节 = 没做过这件事** | `GATE_NO_RECONCILE` |
| `## 未覆盖范围` | 如实列出没审到的部分；**空着或写「无」要附理由** | `GATE_NO_SCOPE` |

三条的语义：

- **`GATE_UNGROUNDED`**：防幻觉。一个"已消除"如果找不到证据，它就不是结论，是声称。
- **`GATE_NO_RECONCILE`**：防以预期为导向。用户明确要求「设想和实际矛盾就重新设想」——**没有这一节，说明从没检查过设想是否成立**。
- **`GATE_NO_SCOPE`**：防为求快而缩小范围。缩小审查范围本身是缺陷，必须显式声明。

**为什么不阻断得太狠**：这三节是**文本要求**，不是数值判据，`gate` 只能查小节在不在、有没有实质内容（>200 字符且非空模板）。**查不到真假，只查有没有做**——这是诚实的边界，写在 §8 已知限制里。

**阈值只是「存在性下限」，不是质量标准（2026-11-10 跨厂商审计指出后修订）**：

`substantive()` 的机械阈值是：表格数据行 ≥3，或多行散文且总字符数超过约 120，且不得语义重复。

**这里刻意不再给「怎么写才能过」的配方。** 原因：本条规则自己承认「查不到真假，只查有没有做」
（见上一段），而一旦再写出「每节 3 条、每条 30–50 字」这种达标写法，这道防阿谀奉承的门
就变成了填空题——照着填就绿，而填进去的东西可以是假的。

> 实证：2026-11-10 的跨厂商审计红队（智谱 GLM-5.3）逐字引用了这一段，指出
> 已删除。

**正确的读法**：三节全绿只证明「这三节存在且非空模板」，**不证明里面写的是真的**。
`gate` 放行时会把这一条打印在「本次放行不覆盖」里。

**另加一条硬要求（v6.29t）**：`## 设想 vs 实际` 这一节，除了要有实质内容，**还必须出现具体的推翻/改写**（推翻/改成/证伪/纠正/错在/实际是…），
或**显式声明"本轮无设想被推翻"**。只写"设想 A 成立、设想 B 成立"会被 `GATE_NO_RECONCILE_CONTENT` 拦下 ——
以前这一节可以靠空泛表述糊过去，等于把"检查过没有"变成了"写过没有"。


**红队产物可以拆分**：`01-cases-devil.md` / `01-cases-tech.md` / `01-cases-domain.md` 等都在检查范围内——R8/R9 就是把多份红队文件拼进 `01-cases.md`，格式与单文件不同，判据必须容忍这种真实形态，否则会误伤真放行轮。

**允许诚实挂零，但必须自述**：某轮真的不开红队（如纯复核轮），必须在 `04-summary.md` 写「本轮无红队交付：<理由>」——`contract` 认这句，`gate` 不认（gate 仍然拦）。**这是刻意的**：诚实记录不等于可以放行，放行必须有人真攻击过。

### 4.1 覆盖度：维度清单驱动

红队只造 20 条，就可能漏掉一整类问题（统计前提 / 伦理合规 / 引用完整性），闸门照样放行。而"未覆盖范围"过去是**主控写的**，等于没审。

- 主控在 `00-target.md` 给**固定维度清单**（八通用 + 类型专属）。**八通用维度**（这是定义，不再交给子代理自行发挥；第 7、8 条为 v6.29 追加）：
  1. **结论 vs 证据**：每条结论是否都能追到一个具体的数字/引文/文件行号
  2. **口径一致性**：同一指标在不同章节/不同稿件里是否用同一个定义与同一组样本
  3. **可比性前提**：跨对象比较时，量纲、采样率、时段、地理/设备条件是否可比
  4. **证据链完整性**：从原始数据 → 脚本 → 中间产物 → 文稿数字，是否每一环都还在
  5. **范围与适用性**：结论的作用域是否被写清（频率范围、样本量、时空覆盖）
  6. **可复算性**：换一个人拿现有文件，能否不靠作者解释复现出同一个数
  7. **版面与体例预算**（v6.29 追加）：交付件是否有硬性篇幅上限（页数/字数），当前**实测**占多少，本轮修订的增量与余额。论文类必须**跑一次排版编译量页数**，不接受"按字数估算"。
  8. **标题页与署名**（v6.29 追加）：作者、单位、通信作者、基金/致谢、作者贡献是否齐全，且与作者信息源逐项一致。**这一类红队历史上 0 命中**——11 维时代没人查过"稿子到底有没有作者块"。
- 红队对每个维度必须填 `覆盖` / `不适用` / `未覆盖`；填"覆盖"必须带 ≥1 个具体检查点指针
- **不许红队自报就算**：让蓝队反向申报"我修的问题属于哪些维度"做交叉；红队说没覆盖伦理却修了伦理 ⇒ 虚报
- **结构性反查（v6.29 硬要求）**：每轮除"该在的在不在"（正向验证）外，必须扫一遍"**不该在的在不在**"——至少覆盖：非目标语言字符（英文稿扫 CJK）、`TODO`/`TBD`/`[待补]`、`[AUTHOR TO COMPLETE]` 类占位符、孤立标题、重复段落。**正向验证永远证明不了"没有混入"。** 实测：主控修完 7 条并逐条验证标记仍在，却在英文稿 L3 留下一段中文编辑说明；R2 未发现，R3 发现。

### 4.2 基准召回：红队质量的可测量指标

红队把致命**漏判**成一般，现有机制发现不了（只有它误判成致命时蓝队能反驳）。

- 维护**历史已确认缺陷集**，每轮混 1–2 条回给红队（回顾式金丝雀），看它能否独立重现
- 未命中 ⇒ 04 标「本轮红队质量存疑」，该轮结论降权
- 没基准集时：每轮**固定抽 3 条**红队判为"一般/优化"的做定向复判，输出"维持/升级"

### 4.3 三态判定（吸收自 `kill-argument`，2026-11-01）

「已修」这个词隐含「曾经坏过、现在补好了」的历史假设，会**系统性地偏向乐观**——蓝队只要把处置写成「已修」，闸门就很难反驳。实测最危险的信号就是「蓝队全盘已修 + 零反驳」。

改用**三态中立判定**，只问事实：**读现在的稿子，这条指控还站得住吗？**

| 判定词 | 含义 |
| --- | --- |
| `当前文本已答` | 现在的稿子已经处理了这条指控，无论它历史上怎么改的 |
| `部分已答` | 处理了一部分，剩下的仍站得住 |
| `仍未解决` | 现在读还是有问题（含「不成立」被判失败、「挂账」未真正登记） |

verdict 映射（照抄 kill-argument 的裁决表）：

| 条件 | verdict | reason_code |
| --- | --- | --- |
| 有未解决的**致命** | `FAIL` | `unresolved_critical` |
| 有任何未解决（严重/一般/优化） | `WARN` | `unresolved_major_or_minor` |
| 零未解决，但有**严重级以上**的部分已答 | `WARN` | `partial_critical_or_repeated_major` |
| 零未解决，只有**一般/优化**级部分已答 | `PASS` | `defense_survives_with_minor_partial_only` |
| 全部已答 | `PASS` | `defense_survives` |

**关键约束**：零未解决但严重级部分已答，**只能 WARN，不许 PASS**。

工具：`node tools/redblue.mjs adjudicate <03-review.md>`

**0 行必须 `UNDECIDABLE`（exit 2），绝不许静默 PASS。** 这是本机制第三次踩同一个坑（M3 编号不认、M6 表式不认、这里判定词不认）——凡「解析出 0 行」，一律当错误处理，不当「没有」。

### 4.4 最强驳回备忘录（吸收自 `kill-argument`，2026-11-01）

平衡式评审会把 5 条弱点平均对待、每条都给点注意力，于是**永远不肯 commit**，结果漏掉「一句话杀死全文」的那一个论点。

红队每轮**额外**产出一段 ≤250 字的「最强驳回备忘录」：**单一连贯论证，不列清单**。

规则：
1. 假设你是最 hostile 的审稿人，目标是让主编读完这一段就拒稿
2. 必须指到 `文件:行号` 或命令输出；指不出位置的论点不写
3. **不许 hedge**（"可能"、"也许"、"某种程度上"），不许提"作者可能已经…"这类缓和
4. 可以复算，能算就把数字写进备忘录
5. 单独放 `02-red-kill.md`，不进判定表

可打的六个轴（挑最狠的**一个**）：结论 vs 证据 / 口径偷换 / 恒等关系被当成错误 / 可比性前提 / 证据链断裂 / 范围夸大。

### 4.5 零上下文红队模式（吸收自 `paper-claim-audit`，2026-11-01）

红队读到 `01-cases.md`、`03-review.md`、上一轮判定，就会**顺着别人的话去找证据**，而不是从稿子本身独立发现问题——这是确认偏误，不是独立性。

`rb-red.yaml` 内置「零上下文模式」：任务包写「零上下文」时，红队**只允许**读：

- ✅ 被审件本身（主张所在文件）
- ✅ 原始证据（数据文件、脚本、原始输出、台账条目）
- ❌ `01-cases.md` / `03-review.md` / `04-summary.md`
- ❌ 主控或蓝队写的任何摘要与复盘
- ❌ 上一轮的判定结论

输出必须额外标 `来源`：`独立发现`（无任何线索提示，自己撞见）或 `复核确认`（主控给了线索，去验证）。**`独立发现` 占比过低 ⇒ 本轮红队质量存疑，结论降权。**

> `paper-claim-audit` 的原话更狠：「This is **stricter than reviewer-independence** — it's zero-context evidence audit.」它的禁止清单甚至包括执行者写的实验日志和叙述报告。红蓝对抗里对应的是：**别让红队读到主控对问题的描述**。

### 4.6 闭环三件套（v6，2026-11-01）

**为什么加这一节**：R1–R3 的技能自审链上，29 条问题从「致命1/严重4」一路收敛到「29 条全部已修、致命0严重0」。看起来完美。但 **R4 用跨厂商零上下文红队一上来就抓到 4 条严重级**——证明"自己审自己越审越松"是真实存在的失效模式，而不是假想。

三个命令把"一轮"变成"闭环"：

#### 4.6.1 `reattack <上轮03> <本轮03>` —— 让「已修」不再可信

「已修」隐含「曾经坏过、现在补好了」的历史假设，是最危险的乐观信号。真正的检验是**下一轮重新攻击同一个位置**。

| 情形 | 判据 | 结论 |
| --- | --- | --- |
| 上轮「已答/已修」+ 本轮「仍未解决」 | 假修复 | **FAIL**（最严重） |
| 上轮「已答/已修」+ 本轮该用例消失 | 静默消失 | **WARN** |
| 上轮「挂账」+ 本轮「仍未解决」 | 预期内 | 只记录 |
| 两轮用例集**一字不差**且全部声称已修（≥10 条） | 没重新攻击 | **SUSPICIOUS** |

最后一条是本轮新增的关键判据：**真正的再攻击必然改变用例集**（旧问题消失 + 新问题出现）。用例集完全不变 = 根本没换人、没换模型、没换视角。

#### 4.6.2 `converge <roundsRoot> [--n=2]` —— 什么时候停

过去闸门只看「这一轮」，红了就进下一轮，但**没说什么时候停**。没有停止条件 = 要么无限循环烧 token，要么凭感觉停。

收敛需**同时**满足：
1. 连续 `n` 轮 致命=0 且 严重=0
2. 用例数不萎缩（本轮 ≥ 上轮 × 0.9）——防止靠删用例"收敛"

#### 4.6.3 `severity <03> [上轮03]` —— 严重度校准

红队会系统性高报（把「一般」写成「严重」以显得有价值），蓝队会系统性低报。

- 全部用例同一级别（且 ≥4 条）⇒ `SEVERITY_NO_GRADATION`，分级失效
- 同一用例跨轮跳变 ≥2 级 ⇒ `SEVERITY_UNSTABLE`，级别不稳定

#### 4.6.4 闭环的完整跑法

```
第 N 轮:  audit → recount → gate → adjudicate
收尾时:  severity(本轮) → reattack(上轮, 本轮) → converge(全部轮次)
```

**三者都绿才算真收敛。** 只有 `gate` 放行不算——那只说明这一轮干净，不说明历史声称的修复是真的。

### 4.7 实跑追加纪律（v6.29，2026-11-08 希腊课题 R1–R3 三连跑沉淀）

下面七条不是设计出来的，是三轮实跑里各摔一次换来的。每条都附当时的实测量。

1. **每轮独立目录，R2/R3 不得塞进 R1 目录。** 否则闸门的 `GATE_UNEXECUTED` 会因为你看到的是上一轮的 `02-blue.md` 而拒绝放行——守卫是对的，别绕。实测：把 R2 放在 R1 目录下，`gate` 直接报"02-blue.md 的逐条处置 0 行"。
2. **主控手工改也必须过新实例复核。** 实测 R3 的全部价值就是它查了主控手改的两处（引用体例 + Declarations），并抓出中文混入正文。
3. **修订必须报增量。** 每轮在 `02-blue.md` 写清"正文词数/页数由 X → Y"。有硬篇幅上限时，**超预算的修订必须做等量删减（净零置换）**，否则红蓝会把稿子一步步推过线。实测：某稿原稿排版 **16 页**，红蓝三轮修复后 **17 页**——修复是对的，但它花掉的那 1 页本来就不存在。
   **⚠️ 后续更正（2026-11-08）**：当时以为该刊有"12 页上限"，后来直接抓官网原文发现**根本没有页数上限，约束是 8,500 词当量（含图表）**。这条纪律（报增量、净零置换）本身仍然成立，但**"上限是多少"必须先核实来源**——见 §4.8 第 6 条。
4. **贴"精确替换块"，不许重写全文。** 格式 `### 修 <编号>` + `--- OLD ---` + `--- NEW ---`，OLD 必须逐字唯一命中。主控用应用器逐块校验，目前已内置三种拦截：`OLD_NOT_FOUND`（逐字不一致）、`OLD_NOT_UNIQUE`（命中多处）、`NEW_HAS_CJK`（英文稿里混入成串中文＝编辑说明误入）。任一不过即 `exit 2`，候选稿不得进复核。
5. **外部素材必须核对归属。** 跨课题共用的"作者信息/基金证明"目录里，文档标题可能是**另一篇论文**的。**能用作者、能用基金，不等于能用标题。** 实测：希腊课题的作者信息文档，标题写的是另一课题（误差补偿）的题目。
6. **"未覆盖范围"必须分两类写**：`环境不允许`（网络、付费墙、沙箱）与 `主控没问人`（期刊硬规则、团队事实这类一问就有的常识）。后者写进报告等于用技术性说法掩饰失职。实测："12 页上限"被列成"沙箱核不了"。
   **⚠️ 这条例子的真正教训比它写的更狠**：那个"12 页上限"**根本不存在**——后来抓官网原文发现该刊是 8,500 词当量。也就是说我不但**把能查的事标成查不了，还查都没查就先造了个约束出来**。
   **⇒ "核不了"三个字必须真的试过才能说。** 那次我只猜了一个 URL 就断定站点打不开；实际换个入口 HTTP 200，一次就拿到了全部作者指南。
7. **红队会多报、会判错，引文必须回原文。** 实测一个课题三轮里红队判错 4 次（拿敏感性变体当主结果 / 比错统计量 / 读错"11 次停用" / 判"附件悬空"），**每次都回原文一眼看穿**。工具侧已提供 `refs <用例> <原文>` 强制回原文；主控不得以二手转述定级。

**本节七条已全部落到命令上**（v6.29）——只写成规则会被跳过，本轮"回原文核对"写成规则照样犯两次，做成命令才止住：

**闭环能力（v6.29 修复）**：`redblue_children` 支持 `action: "continue"`（`child_id` + `prompt`），走 `ctx.subagents.sendMessage`。
把打回意见送回**同一个**执行手，而不是自己重写。**注意**：`startActivation` 的 `childId` 是给新孩子预分配身份，**不是**续接句柄（用它会报 `subagent already exists`）。子代理不可续时红蓝的"打回—修正—复核"闭环是断的 —— 这是 v6.28 及以前一直没发现的断点。

**派活的现实（2026-11-08 实测 18 次 dispatch）**：成功率约 50%，且**失败通知不可信** —— 两个子代理先报失败/只写骨架，后来都交了完整稿。**必须查输出文件，不能凭通知判成败。** 已确认 `agent2api-workbuddy-intl` 是 provider 级不可用（两个模型都失败）。

**归因必须用侧车文件，不许往用例表加列**（v6.29d 实测）：往多表文档加列时，脚本只认第一个表头，会把后面所有表改错位（三轮全部列数混乱，靠备份 zip 才还原）。正确做法：`redteam-roster.json` + `role-map.json` 两个侧车，对文档零侵入。

**按模型的驳回率不是模型好坏排名**（v6.29d 实测混淆）：实测三个模型分别 33.3% / 20.0% / 0%，但 0% 的那个全部来自复核轮（复核只需确认闭合，结构性上很难驳），33.3% 的那个拿的是领域/新颖性任务（那类主张本身最容易站不住）。**报这个数必须同时报它被分到什么任务**，否则就是拿任务难度冒充模型能力。

第八条纪律（v6.29c，由 `quality` 反查逼出来）：**被驳回的主张必须编号，不许写成散文。** 实测代价：某轮里我有两条红队误判（拿敏感性变体当主结果、比错统计量）写进了散文小节、没进编号表 → `quality` 只看得到 6 次驳回里的 4 次，**严重级误报率被低估一半**（机器报 11.1%）。规则：驳回也占一个编号、状态写「不成立」、附反证；否则这一轮的红队质量评估是假的。

第九条纪律（v6.29f）：**收敛前必须做召回标定，且必须用「本项目没用过的模型」打「未修复的交付件」。** 这条规则本技能第 647 行早已写明（"收敛必须由换过红队/换过模型的轮次证明，同一红队连审三轮 = 零证据"），但 2026-11-08 主控仍然违反了它：R3 宣布「已收敛」时，没有任何一轮用新模型重打过整篇稿子。随后换 `minekuai/deepseek-v4.1-flash-1017`（从未用过）零上下文一打，**又找出 5 条前三轮从未提出的缺陷**：删失约定自相矛盾（L59 vs L168）、161/164 把「空对空」计入一致、结论把 anchor 偷换成「正在上报」、KM 日历/时长轴混用、Herfindahl 基线州数无来源。

**这正是"规则只写散文 = 会被违反"的第二次实证。** 已落到机器：`converge` 现在会扫轮次目录里的 `*.score.json` 打出 `RECALL_BASELINE`，找不到就报 `CONVERGE_NO_RECALL_BASELINE`。记住：**`converge` 度量的是同一批红队的复检稳定性，不是覆盖率**；两者必须分开说。

第十条纪律 · **红队任务书必写六条**（2026-11-08 一整夜派活失败与误判换来的，缺一条就会重复已知错误）：

1. **分段读**：稿件有超长单行时（实测某稿 6 行 >1500 字符、最长 3047），先量长行分布，任务书里直接给 `offset/limit` 分段读法。**不要拆成多个小文件**——那会破坏行号，红队就没法引用真实行。
2. **禁止基于截断行下结论**：任务书要明写。实测有红队在自己的证据里带着 `(line truncated)`，据此断言"论文未报告 p 值"，而 p 值就在同一行被截掉的尾部。
3. **先读相邻段落**：实测有 3 条指控的"问题"，正文在紧邻位置已写明（摘要已标 `unadjusted for spatial clustering`、§5.1 已披露 Αττική 占比、§4.5 已写 `Two-layer vacuum`）。
4. **行号 + 逐字引用，不许把参考文献当正文引**：实测有红队把 `L218-L222`（参考文献 3–7）当成 §5.4 正文引用，据此断言"只写了一个陷阱"，而 §5.4 标题逐字写着 "four traps"。
5. **账目闭合检查（必做，独立于"回原文核对"）**：要求红队把稿子里所有计数量列出来，逐个验算 `总数 = 各部分之和`、`比率的分母与分子是否同源`、`同一集合在不同章节的基数是否一致`。
   **实测价值**：主控曾在修复块里自己造了一个 `137/138`（正确是 `138/138`），**逐句回原文核核不出来**；是红队追着 `161/138/141/137` 这几个数不放、发现它们无法闭合，才把它钉出来的。
   **账不平就一定有人错——这是与"回原文"并列的第二条独立核对路径。**
6. **同一说法要搜全稿**：判"已修"之前，必须 `grep` 该说法的**全部出现位置**。实测两次：主控只改了被点名的位置，同一说法在 L176 与 L4/L181 仍在，导致两处"已消除"被后续复核推翻。

这四条命令本身也是摔出来的：`metrics` 第一版对着 16 页的稿子报 `BUDGET_OK`，`scancheck` 第一版对着干净稿报 6 处假阳性 —— **一个会误报「通过」或「有问题」的工具，比没有更糟**，所以两个都改到"宁可说不知道，也不给假绿灯"。

## 5. 严重度判据（4 类）

**分派算法**：先判"流程/规范失效"，再判内容类型。

### 论文 / 报告
| 级别 | 判据 |
| --- | --- |
| 致命 | 结论错误；数据造假或无法复现；核心公式/方法错误；署名问题 |
| 严重 | 关键论据缺失；不可复现；与文献矛盾无解释；统计不足以支撑结论 |
| 一般 | 表述含混、结构混乱、图表不可读、引用缺失 |
| 优化 | 措辞、排版 |

### 数据集 / 脚本
| 级别 | 判据 |
| --- | --- |
| 致命 | 数据本身错误；预处理导致结论反转；口径/单位错误 |
| 严重 | 缺失值处理不当；随机性未固定；缺种子或版本；抽样有偏 |
| 一般 | 命名、注释、日志 |
| 优化 | 性能、可读性 |

### 代码 / 工程
| 级别 | 判据 |
| --- | --- |
| 致命 | 丢数据/越权/安全漏洞 |
| 严重 | 边界未处理、资源泄漏、并发不安全、缺错误处理 |
| 一般 | 命名、结构、重复 |
| 优化 | 可读性、测试补充 |

### 协议 / 规范 / 流程
| 级别 | 判据 |
| --- | --- |
| 致命 | 照它执行**必然**产出错误结论；或存在可静默放行致命缺陷的路径 |
| 严重 | 关键步骤不可执行（引用不存在的函数/字段/文件）；判据不可判定；自相矛盾到影响结论 |
| 一般 | 表述歧义、编号/命名不一致、缺执行锚点 |
| 优化 | 排版、冗余 |

## 6. 证据纪律

- 引用必须指到：**文件 + 行号**，或**命令 + 可复现输出**，或**数据源位置**。
- 蓝队判"不成立"必须附反证（行号/命令输出/数据源三者之一）；**无反证一律计未修**。
- 无法核实的外部说法一律标「未核实」。
- "跑通了"不等于"算对了"：结论性数字要能由原始数据重推。

## 8. 已知限制（不装懂）

1. **同一个模型自己审自己**：红蓝同权重，这是天花板。v6 默认已把蓝队换成 **Spark-x2.6**（跨厂商），这是目前能拿到的最强独立性。
2. **弱独立**：主控把目标、验收标准、红队用例喂给下一方，世界观仍由同一模型框定。
3. **红队只读已升级为强制拦截，但 shell 仍是缺口**（v6.26）：`write`/`edit` 直改被审件会在调用前被 `redblue-write-scope` 的 guard 拒掉；但 `bash`/`pwsh` 的重定向目标解析不出来，`pwsh "echo ... > 论文.tex"` 仍能改。指纹校验保留为第二道，且**仍分不清"谁"改的**。**实测该风险 3 次运行零发生**。
4. **闸门没有外部真值**：致命/严重是模型贴的标签；零确认意味着没人复核。这是换取"不中断"的取舍。
5. **文件契约没有强制力**：跳过步骤不会被拦住，只能靠 `redblue.mjs contract` 事后查。
6. **闸门本质是形式合规**：判 0 不等于没问题。唯一缓解是 §4 的"最需人看的 3 条"。
7. **红蓝偏差方向相反，只压得住一侧**：红队倾向过度升级、蓝队倾向过度降级 → "红判高"被蓝队压住，"红判低"压不住，靠 §4.2 基准召回补。
8. **R2/R3 从未真跑过**：两次实跑都在 R1 就放行或作废，收敛性未验证 → 降为**可选**。（R5 已真跑：`converge --track=skill-audit` 连续干净轮数从 3 掉到 0，见第 14 条。）
9. **解析器的失效方向永远是"少算"，不是"报错"**（2026-11-01 R5 红队实测）。红队构造的 4 份探测复核件里，2 份带致命/严重的被判成 0 行且 `exit 0`：
   - 纯数字编号 `| 1 | 成立 | 致命 |` → 不匹配 `[CNRr]\d` 正则 → 0 行
   - 带连字符编号 `| C-01 | 成立 | 致命 |` → 同上 → 0 行
   - 空表 `（本轮无判定行）` → 0 行且放行
   全部表现为"闸门看到 致命=0 严重=0"。**修法**：编号正则接受 `字母±连字符+数字`、中文编号、纯数字；`recount`/`gate` 在 `rows.length === 0` 时必须 `exit 2`（空表不是"没问题"，是"没结论"）。
10. **「级别列」会被「状态列」掩盖**（2026-11-01 R5 红队 N05 抓到，最致命）。旧格式 `| 编号 | 级别 | 状态 |` 里，状态词（已修/未修）决定分桶，**级别列被整个丢弃**。实测 10 行 `| C01 | 致命 | 未修 |` → `recount` 报 `致命=0 严重=0 挂账=10`；10 行 `| C01 | 致命 | 已修 |` → `致命=0 已消除=10`。**无论修没修，「致命」都被清零**。修法：状态列决定桶，级别列另存 `claimedLevel`；`recount` 额外打印「未结案的真实严重度」，`gate` 对两个来源取大值。
11. **`bundle` 只核范围不核内容**（R5 红队 N02）。造一份 5 行的 `protocol.md`、第 5 行随便写，复核件声称该行写着某段话 → `bundle` 输出 `OK` exit 0；同一条引用改用 `cite` 带引文则 `CITE_FAIL` exit 1。**行号检查对内容真假零分辨力**，所以"引用可落地"不能当作"引用属实"。
12. **`cite` 不带引文时静默通过**（R5 红队 N12）。唯一能机械核引用的命令，在缺引文时只打印该行内容并 exit 0 —— 现在改为 `CITE_LINE_UNVERIFIED` + exit 2。
13. **两个命令可以对同一批数据给出相反结论**（2026-11-01 R5 红队第二实例 S02 抓到，致命级）。实测 `reattack R2-convA R2-convB` → `REATTACK: FAIL (false_fix_detected)` exit 1，而同一批目录 `converge --n=2` → **`CONVERGE: PASS (converged)` exit 0**。根因：`converge` 自己实现了一遍收敛判据，**从不调用 `cmdReattack`**。修法：`converge` 增加条件 2b——若上一轮某条写「已修/当前文本已答」而本轮同编号写「仍未解决/未修/成立」，直接判 `NOT_YET`。**收敛的定义里必须包含「上轮声称修好的，本轮没被重新打开」，否则"收敛"只是"数字变小"。**
14. **被审对象在审计期间被改写 = 审计结论无锚点**（2026-11-01 R5 元教训）。R5 期间 `redblue.mjs` 被改写 8 次（48791 → 77271 B），两个红队实例钉的是 `2D08094C374E`(58684B) 与 `0EDDB234BAF4`(63193B)，相差 4509 B —— **「已修/未修」结论只对某个瞬时快照成立**。**规则：每轮开工前主控先写 `00-frozen.txt` 冻结 `SKILL.md` 与工具 sha256；红蓝报告必须绑定该哈希；哈希对不上的结论一律作废重跑。**
15. **红队的价值来自「实际运行」，不来自「读文档」**（2026-11-01 R5 实证）。R1–R4 四轮文档审阅报 0 致命；R5 让红队**自己造 20 个探测件、跑 `recount`/`gate`/`severity`/`converge`/`reattack`/`bundle`/`adjudicate`/`cite`、看退出码**，一上来抓到 2 致命。**任务书必须写明：先钉快照 → 再造探测件 → 再实际运行 → 再看预期与实际的差异。** 只读文档的红队会重演 R1–R3 的假收敛。
16. **多文件技能包会静默退化**（2026-11-01 实测）。R3 审计时引用了 5 个文件，R5 开工时只剩 1 个 —— 56 处 `文件名:行号` 引用全部悬空，而没有任何检查报这件事。**修法**：`bundle` 从复核件提取所有 `名:行号` 引用并核实文件存在与行号范围；`audit` 以 `bundle` 为前置门，不通过直接 `ROUND INVALID`。
17. **压缩正反馈：同一文件被整篇重写，把上下文撑爆**（2026-11-02 实测两会话原始日志）。`7ba84461` 13 轮里触发 **40 次压缩**（turn 12 单轮 13 次），摘要长度从 19,752 B 涨到 **87,006 B**（无嵌套摘要标记，是**有机增长**，不是套娃）。量化根因不是"压缩本身写得长"，而是**主控把同一份产物整篇重写**：
    - `03-review.md` 被 `write` 整篇写 **15 次**、累计 **130,577 B**（最终文件仅约 13 KB）
    - `01-cases.md` 6 次 / 66,301 B，`01-cases-domain.md` 6 次 / 48,381 B，`00-target.md` 7 次 / 45,691 B
    - **同文件重复写的纯浪费 = 346,180 B，占全部 write 字节的 57%**
    - 对比：`stream` 流式 chunk 8.43 MB / 25.3%、`content` 正文仅 2.98 MB / 8.9% —— **对话内容本身不大，是反复重写把它放大了**
    **硬规则（v6.24 起必须遵守）**：
    - **产物只增不改**：`01-cases.md`、`00-target.md`、`03-review.md` 一律 `append`（用 `edit` 追加小节），**禁止 `write` 整篇覆盖**。要改旧结论就新增「## 修订记录」小节并注明推翻哪一条，保留原文。
    - **不在对话里贴大段产物**：写完文件后只报「已写 X，N 行，sha256 前 8 位」，不复述内容。
    - **单轮产物预算**：每轮 6 个文件（`00`–`05`）+ 证据文件，单文件超过 20 KB 就该拆分而不是重写。
    - **压缩是症状不是病因**：摘要变长说明前面步骤在反复重写同一批文件。遇到连续 3 轮压缩，先查 write 次数，不要靠"压缩写短一点"治。
18. **闸门从不问「这一轮真的有人攻击过吗」**（2026-11-02 `R10-1102a1` 实测假放行，最危险）。两路红队都没启动、蓝队子代理失控、`02-blue.md` 全由主控代笔，`03-review.md` 仍写「20 条全部已消除」→ 旧闸门 `GATE: 放行` exit 0。R11 两路独立红队（5 条 + 8 条）复核后推翻为「13 通过 / 6 未彻底 / 8 新发现」，留下元教训「**主控自判不可靠**」。修法：闸门新增 `GATE_UNATTACKED`（红队无交付）与 `GATE_UNEXECUTED`（蓝队无处置行）两道硬拦，见 §4.0。
19. **表外一般/优化被完全无视**（2026-11-02 实测）。3 条表外行（一般 2 + 优化 1）配一张干净判定表 → 旧闸门 `GATE: 放行` exit 0。修法：表外「一般+优化」超过容差 3 条即不放行；致命/严重 1 条即不放行。
20. **`contract` 对 R2+ 从不检查红队产物**（2026-11-02 实测）。`INHERITED` 让 `01-cases.md` 在 R2+ 无条件算"继承"：文件完全缺失时仍打印 `CONTRACT_OK(继承): 01-cases.md 由上一轮提供`。修法：R2+ 缺 `01-cases.md` 时必须由 `04-summary.md` 自述「本轮无红队交付」，否则 `CONTRACT_VIOLATION`。
21. **「转抄上一轮」被当成「本轮有人攻击过」**（v6.25，R10 第二次假放行的真正原因）。给 R10 补上 `GATE_UNATTACKED` 后，它**又被放行了**：因为 R10 的 `01-cases.md` 开头写「# R10 用例清单（**继承 R9 红队 13 条** + 主控撤回 2 条）」，正文是上一轮的转抄，里面有完整的「编号+级别」判定行 —— 第一版判据只查「有没有判定行」，于是判它已交付。**转抄 ≠ 攻击。** 修法：文件开头 12 行内自述「继承/沿用/转抄上一轮」⇒ 判 `GATE_UNATTACKED`。只看开头是为了不误伤正文里合法的历史引用（如「R1 为何漏」）。
22. **新判据回溯旧产物会全部判死**（v6.25 实测教训，通用规律）。给闸门加「实事求是三节」（证据落地/设想vs实际/未覆盖范围）后，回溯 11 轮真实数据：R8、R11 这两个**历史上真放行**的轮次全被拦下。不是旧轮次有问题，是**旧轮次没有这三节的标题**——它们写的是「纪律核验」「主控决策」「未关闭项」，功能等价。**判据必须认历史真实形态**，否则每次加严都会把真放行判成假放行。修法：每节都接受等价标题（`纪律核验`/`主控决策·改判`/`未关闭项·待办`），两者都没有才拦。
23. **判据阈值定在中文上是纯拍脑袋**（v6.25 实测，连错两次）。「三节是否有实质内容」第一版用「>200 字符」，把一份内容完整的中文小节（137 字符、2 行数据表 + 2 句论断）判成「缺实质小节」；改成「表格行 ≥3 且散文 ≥60」后，另一份同样完整的（prose=54）**差 6 个字符**又被拦。**中文字符信息密度约为英文 3 倍，照搬英文字数阈值必然过严。** 最终判据：**表格数据行 ≥3 即算做过**（表格本身就是证据），否则要求 `表格 ≥2 行 + 散文 ≥30`。**教训：判"有没有做这件事"不要用字符数卡，用结构行数。**
24. **`ask build` 会产出空清单**（v6.25 实测）。最新一轮 `R12-1104a1` 只有目录、没有 `03-review.md`，生成器直接取最后一轮 → 判定表 0 行 → 「未结案 0 条」→ **03 待决问题清单是空的**，而这份清单正是求助包的核心。修法：回退到「最近一个有 `03-review.md` 的轮次」，并在输出里注明跳过了谁。
25. **求助包里的「位置/证据」全是「—」**（v6.25 实测）。各轮判定表列序完全不同（R11 表头是 `| 用例 | 级别 → 处置 | 位置 | 现值与理由 |`，位置与理由合并在最后一列），`parseVerdict` 抽出的 `loc`/`ev` 常是 `undefined`，写进求助包就成了「—」——**外部 AI 拿不到任何可判断的信息**。修法：按编号回查 `03-review.md` 与 `01-cases*.md` 的**原始行，原样贴出整行**，不再依赖解析字段。
26. **「没办法」是模型最容易自我批准的门**（v6.25，设计约束而非缺陷）。用户要求「穷尽之后才许找你」，但"穷尽"由模型自己判，等于没有门。修法：`ask check` 把穷尽拆成 5 条机械判据（红队两路/蓝队≥2修法/工具跑过/≥2轮/卡点性质），前 4 条自动判，**第 5 条「卡点是不是外部事实」查不了，所以强制人工在 `_ask/00-gate.md` 写一行声明**——不写就不许生成求助包。这是全机制唯一一处要求人写字的地方，因为它是"找用户"这道门本身。**能机械查的查，查不了的留痕但不装懂。**
27. **10 分钟自动续跑不能靠模型自觉**（v6.25，设计约束）。用户要求「10 分钟没人理就自己继续」。写进提示词等于没写——R10 已实证主控会自我放行。修法：落盘的 `_auto.json` 状态机（`auto arm/beat/check`），`check` 退出码 0=还在跑/1=超时必须自己继续/2=已收工。**记忆在文件里，不在上下文里**——这样换一个全新子代理接手也能凭它继续，不依赖任何对话历史。

## 9. 实战经验（2026-10-31 两轮实跑 + 一次外部独立复核）

1. **"蓝队全盘已修 + 零反驳"是最危险的信号**。实测三次：20 条全已修被打回 8 条；12 条全已修被打回 2 不属实 + 2 部分属实；18 条 17 已修仍被抓出 6 处新错。**必须派复核红队实跑**。
2. **给子代理设显式落盘时限**。实测有子代理跑 20 分钟零输出；重试时写"最多 8 次工具调用就必须让文件有内容"，4 分钟交卷。
3. **迟到的子代理会覆盖已落盘的产物**。超时重试时原实例可能仍在跑——**重试必须写不同文件名**，落盘后立刻转存。这是唯一造成过整天重跑的真实故障。
4. **复核红队会顺手抓到上一方的自述错误**（行数、行号、统计口径），这类"元错误"不在原用例里，是"能复算就复算"的副产品。
5. **协议自身每跑一轮就被审出 bug**。第一次是"挂账上限"公式在零严重时误判超限；第二次是统计脚本认不出「致命 → 已消除」的箭头写法。
6. **脚本必须能真的跑起来，且要自带自检**。外部复核把 v3 的 8 个 bash 脚本抽出来实跑，抓到 4 个 bug（最狠的是 mawk 按字节匹配 `[（(]`，把「一般/优化/已消除」截断成未识别）；而目标机器根本没有 bash，8 个脚本一次都跑不起来。现在是 1 个 Node 文件 + `selftest`。

7. **「连续干净轮数」会骗人，因为它只看最后几轮的数字**（2026-11-01 R5 实证）。`converge --track=skill-audit` 对 R1/R2/R3 报「连续干净轮数 = 3」→ 看起来已收敛；R5 一进来报 `严重=2`，干净轮数**掉到 0**。R1–R3 的"干净"是同一批人反复审同一批用例审出来的，不是独立验证。**判据：收敛必须由「换过红队/换过模型」的轮次证明，同一红队连审三轮 = 零证据。**
8. **闸门修得越严，越要防它把真问题也拦掉**（2026-11-01 R5 实证）。本轮加了 5 条 `exit 2` 守卫（空表、0 行、编号不匹配、跨课题、假修复）。每一条都可能把"合法但格式不同"的复核件误判为"不可判定"。**规则：新增 `exit 2` 必须同时给出一条"如何修好再跑"的提示**，否则下一轮的人会卡在那里不知道怎么过。
9. **红队报告自己也会数字打架**（2026-11-01 R5 实测）。第一实例自报「致命=8 严重=10 一般=6 合计=24」，而 `recount` 对它自己的 `02-red.md` 读出 `致命=6 严重=15 一般=34 合计=55` —— 因为它写了两张表（25 行主表 + 29 行复核表），工具没有多表消歧。**红队的自述统计一律不采信，必须用工具重算。**
10. **子代理"看起来在做"和"真的交卷"是两件事**（2026-11-01 实测）。红队跑到 step 22、读了 20 多个文件、写了复算脚本，但 `02-red.md` 一直是空骨架，直到 04:30 才一次性填满。**必须在任务包里强制"先写骨架、每判完一条立刻追加"**，否则超时即全丢（实测 spark 蓝队跑满 30 min 被 `ETIMEDOUT` 杀掉，产出 0 字节）。
11. **`reasoningEffort` 会直接杀死子代理**。LongCat-2.5-Preview 不支持 `high`，子代理在第一个 turn 就以 `UNSUPPORTED_REASONING_EFFORT` 失败、零输出。名册 YAML 里**不要写**这个字段，除非确认模型支持。
12. **统计脚本的"静默 0 行"是最危险的缺陷**。红队把判定表写在 `# R4 红队复攻` 标题下、列序改成「用例|判定|级别|位置|证据」，`recount` 就数出 0 行并 `exit 0` —— 闸门等于瞎的。现在 `parseVerdict` 不再依赖小节标题，同时认两种列序。
13. **闸门必须能看见"表外"的严重发现**。真实发生过：判定表干净（一般=1 已消除=11）→ 脚本 `GATE: 放行`，但正文里藏着 1 条严重 → 主控人工否决。现在 `scanOffTable` + `scanStraySeverity` 双保险。
14. **侧边栏/子代理看板一直都有，只是要找对地方**（2026-11-01 实测）。它在会话标题栏的「N 个子智能体」下拉里；独立的「子代理看板」面板需要先选中会话才填充顶部计量圈，但列表本身一直完整。`delegate` 派出的子代理会实时出现在里面（`正在运行` / `已完成` / tok / 耗时），headless 独立进程则**永远不出现** —— 这是选名册方案的决定性理由。
15. **「29 条全部已修」是本机制最危险的一次假收敛**（2026-11-01 实测）。R1-skill-audit 致命1/严重4 → R2 严重1 → R3 致命0/严重0、29 条全已修。看起来收敛了。但 R4 换跨厂商零上下文红队，一上来就抓到 4 条严重级。**根因**：`reattack` 显示 R1→R2→R3 三轮用例集**一字不差**（C01–C29 全同）—— 那不是"修得好"，是"根本没重新攻击"。同源审同源，必然越审越松。
16. **「已修」这个词必须被机器否定一次**。`reattack` 的核心判据不是"上一轮说修好了没有"，而是"这一轮重新攻击它还站不站得住"。上轮已答 + 本轮仍未解决 = 假修复（FAIL）；上轮已答 + 本轮用例消失 = 静默消失（WARN）。**两种都不许 PASS。**
17. **解析器的"合法输入骗过它"比"0 行"更隐蔽**。本轮修了三个解析缺陷：不认 `R01` 编号（9 行只数 4 行）、不认旧格式「—|已修」（29 行全跳过）、`raw` 存了级别列而不是判定词（三态信息整个丢失）。**每一次都表现为"少算"而不是"报错"**，闸门按错误的低计数放行。修法：凡是"行数少于肉眼可见"就必须当 bug 处理。
18. **技能文档的多文件结构会静默退化**。R3 审计时引用 5 个文件（`SKILL.md`/`protocol.md`/`red-brief.md`/`templates.md`/`blue-brief.md`），R5 开工时目录里**只剩 `SKILL.md`**。所有引用那 4 个文件的行号/条款全部悬空，而没有任何检查会报这件事。**修法**：`audit` 必须先核交付件集合，缺文件直接 `ROUND INVALID`。


## 10. 实战经验（2026-11-08，希腊课题 R1–R10，**机制侧**）

> 这一夜的产出不是"改好了某篇论文"，而是把 37 项改动落到命令上。
> 每条都附实测量；没有实测量的不写。

### 10.1 新增命令（都已接入 `gate`，不跑就等于没过）

| 命令 | 查什么 | 不跑会怎样 |
| --- | --- | --- |
| `ident <spec.json>` | 账目恒等式；值可**用正则从正文抽取**，抽不到即 `IDENT_VALUE_MISSING` | 数字互相矛盾却无人发现 |
| `occur <spec.json>` / `occur draft` | 某说法**应剩几处**；`draft` 先实测再生成骨架 | 「改完只改一处、别处还在」 |
| `xcheck <file>` | 同一量两条独立路径算（行数/词数/**两个解析器互校**） | 工具自己算错也发现不了 |
| `attack record` | 把"谁审了哪一版"绑到交付件 sha256 | "attacked" 只是名义上的 |
| `attack record-ext` | 登记**机制外**独立评审（外部 AI / 跨厂商），`converge` 认它 | 单 provider 机器上永远无法证明"换过红队" |
| `carry` / `route` / `canary` / `quality` | 丢旧账 / 真实模型清单 / 召回标定 / 精确率 | 靠遗忘收敛、拿网关模型当已配置 |

### 10.2 加任何一条新判据之前，必须问三件事

1. **它真的在执行吗？** 实测踩过：判据写在 `if (fatal===0 && severe===0)` **里面**，而严重项>0 时根本进不去 —— **死代码**。
2. **它能被绕吗？** 实测三条形态判据被我各绕过一次（随便填行号 / 写"设想 A 被推翻"却不说是哪条 / 用只出现一次的无关长词当锚）。
3. **它会误伤历史真实形态吗？** 实测两次：R9 用「设想/实际/改成什么」三列表格被判死；R10 跨轮引用 `N6` 被判"编造编号"。

**三问缺一条，新判据就会变成假护栏或误伤源。**

### 10.3 `catch` 包住判断逻辑时必须 fail-closed

实测：某判据块引用了未定义的变量（`rdA2`），抛 `ReferenceError` 后被 `catch {}` **静默吞掉** ——
**判据"看起来有护栏、其实一行没执行"**，而自测断言还是"通过"的。
**只有包住数据读取时才允许静默跳过。** 判断逻辑类 catch 必须打印痕迹并 `return 1`。

### 10.4 「严重」必须核出来，不能拍出来

主控曾三次把非严重的事定成严重：编造的 `137/138`、**假设出来的"12 页上限"**、
以及"14 条文献 0 处引注"（实查 14 条**全部**被引注，正文用的是内联 DOI）。
⇒ `GATE_SEVERE_UNVERIFIED`：严重项的证据里必须出现可核方法名；
**凡是"缺失类"断言（0 处/从未/not cited），必须 ≥2 条独立方法支撑** ——
因为声称"没有"时，换个方法往往就找得到。

### 10.5 覆盖率自检：让自测自己证明护栏被执行过

`selftest` 拦截 `console.log`/`console.error`，收集本次运行**实际出现过的诊断码与成功标记**，
末尾与必需清单核对：**42 个诊断码 + 13 个成功标记全部被触发过**（2026-11-10 跨厂商审计按代码实数；此前写 38+12 已过时）。
在此之前"全绿"只说明"跑过的用例没报错"；现在它还说明"每道护栏至少被执行过一次"。

### 10.6 三个平台/语言级的坑

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| **BOM** | Windows `Set-Content -Encoding utf8` 写 BOM，`JSON.parse` 报 `Unexpected token '﻿'` | 统一走 `readJsonFile()`（`replace(/^\uFEFF/,'')`）。一天遇到三次 |
| **`RegExp.test` 带 `g` 有状态** | 逐行扫描会跳行、计数偏低（**21 处数成 19 处**） | 每行前重置 `lastIndex`；并加回归测试 |
| **列错位** | 「级别」与「状态」写反 → 12 条"已消除"被统计成"一般=12"，**四个命令同时被污染** | `detectColumnSwap`：用词表互斥性检测，`SUSPECT_COLUMN_SWAP`/`GATE_COLUMN_SWAP` |

### 10.7 两条通用方法论

1. **两个独立实现给出的数不一致时，不要挑一个信，去写第三个。**
   今天用它三次：账目闭合抓出编造的 `137/138`；`occur` 三方互校抓出 `lastIndex` 计数偏低；DOI 核对推翻"文献未引"。
2. **"核不了"三个字必须真的试过才能说。**
   我把"期刊页数政策"标成"沙箱核不了"三轮，实际**猜错一个 URL** 而已 —— 换个入口 HTTP 200，一次就拿到全部作者指南，并当场推翻了那个"12 页上限"。

### 10.8 主控自己会造数与改错数（必须认）

| 类型 | 实例 | 抓法 |
| --- | --- | --- |
| **造数** | 修复块里编出 `137/138`（原稿里 `137` 只出现在端点编号 `S013701` 和 DOI 页码里） | 账目闭合 + 回原文搜该数字 |
| **过度纠正** | 把**本来正确**的 Herfindahl 基线 `23 州/0.043/6.1×` 改成 `26 州/0.0385/6.9×`（23 = 至少有 1 起死亡的州数，1/23=0.0435 正是原稿的数） | 回原始数据重算分母 |
| **凭猜填期望** | `occur` 的 spec 里把 `161/164` 的期望写成 3，实查 4 处 | `occur draft` 先量再写 |

**共同点：改完之后账仍然自洽，只有回原始数据重算才看得出来。** 所以"账目闭合"必须**从正文抽值**，不许手抄。

### 10.9 第 4 类错误的形状：**量的范围划错**

今天四次误判，没有一次是算法错，全是**范围错**：

| 我以为 | 实际 | 范围错在哪 |
| --- | --- | --- |
| 超 12 页上限 | 根本没这个上限，是 8,500 词 | **约束本身没核实来源** |
| 摘要 301 词 | 284 词；301 = 284 + 17 个关键词 | 把关键词算进摘要 |
| ref6/ref12/ref13 从未被引 | 全被引，正文用的是 DOI | 只按作者姓氏检索 |
| 正文残留 13 处 DOI | 正文 0 处；13 个在参考文献表 | 数了全文而非正文 |

**对策**：`occur` 现在**无条件打印扫描范围**，并支持 `"scope": "body"`。

> 通用纪律：凡是"计数 / 搜索 / 核对"类判断，**先声明作用域再报结果**。
> 「命中 13 处」这句话本身不完整 —— **在哪个范围里命中 13 处**才是可核的命题。

**这条和 §10.4（严重必须核过）是一对**：10.4 管"级别怎么定"，本条管"数是怎么数出来的"。
两者合起来覆盖了主控今天全部 7 次错误里的 6 次。

### 10.10 第 8 类错误：**把字符串序当成时间/版本序**

2026-11-08 收尾时发现：`dirs.sort()` 是字典序 → 轮次变成 `R1, R10, R2, …, R9`，
于是 `converge` 把 **R9 当成最新一轮**，整晚报的「连续干净轮数 1 < 2」**是假的**；修后合法 `PASS`。
同一 bug 还让 `gate` 拿 **v7** 的指纹与行号去核 **v13**（`v13` 字典序排在 `v7` 前）。

修法：`natCmp`（数字段补零后比较），4 处排序全部改掉。

**这与 §10.9 是同一家族**：10.9 是"量的范围划错"，本条是"序的口径划错"。
两者都**不是算错，是答错了问题**。
'> 凡是按名字排序拿到"最新"的地方，先问一句：**这个名字序等于时间序吗？**

### 10.11 第 9 / 10 类错误：两命令不交叉、以及"量退出码过了截断管道"

**第 9 类：两条命令查不同文件，从不对账。** `gate` 查 04-summary 的证据小节，`bundle`/`audit` 查 03-review 的 `文件名:行号`。
实测 R10：`bundle` 判 `UNDECIDABLE`（整份复核 0 处 `文件名:行号`），`gate` 照旧「放行」——**同一份数据结论相反**。
10 轮全扫，**7 轮命中**。修法：`gate` 加 `GATE_LOCATION_UNRESOLVABLE`（只报不拦）。
**凡是有两条命令碰同一批数据的地方，都要问一句：它们会不会得出相反的结论？**

**第 10 类：退出码不许过截断管道。** `node ... | Select-Object -First 3` 会让 node 收到 EPIPE、退出码变 **-1**，
我据此误判 `auto status` 有 bug，直接跑其实是 **exit 0**。**量退出码要用独立一次调用，不要接在会提前关闭的管道后面。**

**本轮还有个"写对了但没接线"的坑**：`GATE_LOCATION_UNRESOLVABLE` 第一版按 `r['级别']` 过滤，
而 `parseVerdict` 的行对象里取不到「级别」列 → 过滤后 0 条 → **提示从未触发**；第二版放在 `GATE_UNATTACKED` 之后 → 被早退挡住。
**判据要验证"真的会响"，不是"代码写了"。**

### 10.12 注释承诺的修复，必须核实它真的接线了

**第 11 类错误：注释写得很肯定，代码里没有。** `bundle` 的注释写着「修法：要求每条引用附带引文……
**第 11 类错误：注释写得很肯定，代码里没有。** —— **⚠ 2026-11-10 已补上**：`redblue.mjs` 现在会统计未附引文的引用并打印 `BUNDLE_UNVERIFIED`（跨厂商审计 讯飞 Spark 指出此处仍按"未修"叙述）。以下是当时的原始记录：
`grep UNVERIFIED` 只找到 gate 和 cite 的同名码。**读者会以为已经修好了。**
规则：**凡是注释里出现「修法：」「已改为」「现在补上」这类完成时态的句子，都要 grep 一次那个诊断码/函数名，确认它真的存在。**

**第 12 类错误：解析成功不等于解析得对。** `bundle` 找到 `06-candidate-v5.md` 时说 OK，
但它解析到的是 **R9** 的副本（R10 目录里没有 v5）—— 跨轮静默替换。
规则：**凡是"按名字找文件"的命令，成功分支必须打印解析到的完整路径**，
否则「找到了」和「找对了」分不开。

**自测教训**：两条断言共用一个捕获数组时，**先快照再清空** —— 清空是为了隔离，不是抹掉前一条的证据。

### 10.13 第 13 类错误：关键词子串不等于「那节存在」

`salvage` 用 `body.includes('逐条处置')` 判断小节在不在 —— 于是**文件里写「本文没有『逐条处置』」
也算有这个小节**，命令判 `SALVAGE_OK`。实测造一份三个文件都明写"没有 XX"的轮次，直接通过。
修法：关键词至少要有一次出现在**非否定语境**下（`没有|不含|并无|未|非|缺|漏|省略|跳过|无` 紧邻在前则不算）。
**推论：凡是拿"某词出现过没有"当判据的命令，都要问一句 —— 把那个词放进否定句里，判据还成立吗？**

**另一条同样重要**：`salvage` 这条命令**当时每天都在跑，却从未进过自测**。**⚠ 2026-11-10 已补**：自测里现有 `SALVAGE_OK` 与 `SALVAGE_NEEDED` 两条断言直接调 `cmdSalvage`。以下是当时的原始记录：
**命令清单 ≠ 已测清单。** 新增/修改任何命令时，顺手 grep 一次它在自测里有没有断言。

### 10.14 第 14 类错误：把「我没复现」写成「未证实」

实测（2026-11-09，LongCat 工人核 R10 的 N24）：它用 5 种分词方法得到 280/277/297/304/309/317 词，
都不等于复核件声称的 291，于是标 `UNVERIFIED` 并建议「人工确认词数口径」。
**第 6 种方法（按 ASCII 词边界切分连字符/撇号复合词）正好得到 291** —— 摘要里恰有 24 个连字符复合词。
复核件写的「280/291 词」是**两种口径并列**，不是矛盾，两种口径都 ≤300。

**规则：任何「未复现 / 未找到 / 不存在」的结论，必须同时报告「我试过哪几种找法」。**
只报结论不报方法的缺席断言，一律按「未验证」处理，不许当成发现转给用户或写进报告。
这条和 §10 早期的「单方法缺席断言」是同一类，但它更隐蔽 —— 因为报告人**确实试了 5 次**，
看上去很勤奋，只是方法覆盖不到。

**配套教训（监工侧）**：同一轮里我自己也出错 —— 查「`137/138` 在不在 v6 L165」得 false，
一度判定工人报错了；实际 `137/138` 只在 **v5**，v6 L165 已是修好的文本。**监工也会查错文件，
第一遍不能当结论，必须换一个文件/方法再验一次。**


### 10.15 第 15 类错误：把「机制内换不到模型」当成「无法收敛」，于是永远 NOT_YET

**实测（2026-11-10，R14）**：`converge` 硬要求「换过红队/换过模型」，而本机只有
`deepseek-account` 一个 provider。所有轮次都是「同模型不同实例」，于是 `converge`
在这台机器上**物理上永远无法 PASS** —— 判据没错，但它把一个**环境限制**写成了**质量结论**。

而 R14 真实发生过的事是：把三份求助 MD 交给 **5 个外部 AI**（hy / mimo / ds / 豆包 / qw），
它们在同一批问题上给出了**实质分歧**：

- 4 票：「`n=1` 风险集使 log-rank 不可解释」
- 1 票（qw）：「那个时点 O−E=0、V=0，根本不进统计量」

主控据此实算，发现**双方都不对**：2006-12-18 时 late 组风险集 `n₂=0`，该点贡献确实是 0（qw 对）；
但真问题也不在 `n=1`，而是 **`χ²` 的 71.2% 来自 2015–2017 那 4 个「early 只剩 2–5 人」的临终时点**
（leave-one-out：删这 4 点 `8.524→2.452`；仅留 `n₁>5` 的时点仍 `7.097`，`p≈0.008`）。

**这是真正的跨厂商独立证据，价值远高于「同 provider 的又一个实例」，机制却完全看不见它。**

**规则**：机制外独立评审必须能用 `attack record-ext <轮次> <来源> <交付件>` 登记，
且 `converge` 必须认它作「换过红队」的有效证据（只认**当前交付件指纹**的，换版自动作废）。

**配套踩坑（同轮修掉）**：`staticSet` 只报**第一个**「编号相同的相邻对」，而 R12→R13 往往先撞上
（同套 21 条一字不差），循环在那里就 `break` 了 —— R14 登记的 5 份外部评审**永远轮不到被看**。
收敛关心的是「**最近**有没有重新攻击」，不是「历史上哪一对先冻结」，所以判断必须在循环外
先看**最新一轮**。

**通用形状**：任何判据都必须能区分「判据未满足」与「该判据在本环境不可满足」。
后者应当报 `ENV_LIMITED` 并允许替代证据，而不是日复一日地报同一个 `NOT_YET`。

### 10.16 第 16 类错误：`bundle` 的 OK 只证明「行号在范围内」，不证明「那行是什么」

**实测（2026-11-10，R14）**：R12 / R13 / R14 **三轮**的 `03-review.md` 都引用
`S10_midpoint_sensitivity.txt:4` 并声称那是 `Jan-1 (main),6.26,8.82,3.82` 行 ——
**而 S10 原文件只有 5 行，`:4` 实际是 `Jul-1 (midpoint)` 行**。

`bundle` 三轮全判 OK，因为它只检查 `maxHi ≤ 行数`（4 ≤ 5 不越界）。
直到本轮复核员写到 `:6`（越界）才暴露。**它自己也一直在报 `BUNDLE_UNVERIFIED` 并提示**
`cite <文件:行号> --quote="该行原文"`，**但本项目 14 轮没有一轮用过 `cite`。**

**规则**：
1. 引用「某个数字/某句话」作为结论依据时，光有 `文件:行号` 不够，必须 `cite --quote` 把该行原文固定下来。
2. 引用**统计结果**时，必须写明**算法口径** —— 同轮的另一处教训：
   v16 原写 `removing the four event times` 得 `χ²=2.452`，而按字面「删掉那 4 行」是 `7.556`。
   `removing` 与 `censoring` 是两种算法，**读者按字面能复算出不同答案 = 给审稿人递刀**。
   已改为 `censoring … at their observed times (their risk-set contribution is retained; only their event status is set to censored)`。

**通用形状**：所有「可落地」类检查（文件存在 / 行号在范围 / 引文非空）都只验证**形状**，
不验证**语义**。形状全过而语义全错，是本项目最常见的假绿灯。
读闸门输出时，`OK` 一律读作「形状通过」，不读作「内容正确」。

### 10.17 第 17 类错误：把「我没去找」当成「环境没有」——本轮最贵的一次

**实测（2026-11-10，被用户当面纠正）**：

主控在 **R11 到 R14 四轮**里，一直对用户和文件里写同一句话：

> **⚠ 下面这句是 2026-11-10 被推翻的错误判断，保留作反面教材：**
>
> 「本机只有 `deepseek-account` 一个 provider，所以所有红队/蓝队都是『同模型不同实例』的弱独立，
> `converge` 永远无法证明『换过红队』。」

基于这个判断，还专门设计了一条绕路（`attack record-ext`，让用户手工把三份 MD 转给 5 个外部 AI，
再把意见粘回来登记）。

**用户一句话推翻**：「不是说了吗？模型自己在除了 ds account 之外的随便选，也就是我能用哪些你就能用哪些。」

实测结果：

| 事实 | 值 |
| --- | --- |
| `route` 命令列出的 provider | **14 组**（含 `agent2api-accio` 42 个模型：`claude-opus-4-6` / `claude-sonnet-4-6` / `gemini-3-flash-preview`；`agent2api-catpaw` 8 个：`kimi-k3` / `MiniMax-M3` / `deepseek-v4-pro`） |
| `subagents\*.yaml` 里的具名库 | **4 个**，全部配了真跨厂商模型 |
| `delegate(library_id="rb-devil")` 实测 | **成功**，模型自报「Kimi（Moonshot AI）」 |
| 失败的那一个 | `rb-red` → `agent2api-qoder/Kimi-K3.1-Pro`，**qoder 余额为 0**（不是"没有这个模型"） |

**真正的原因**：主控在四轮里**全部用 `longcat_worker`**（它的 `provider`/`model` 在
`cordis.patch.yml` 里**钉死成 `longcat/LongCat-2.5-Preview`**）充当红队、蓝队、复核——
所有角色同一个模型。而四个跨厂商具名库从头到尾**一次没用过**。

**为什么 `route` 没能拦住这个错误**：它当时只打印「provider → model 清单」，
末尾一句「配置里存在≠上游可用」就结束。**它给了答案，没给用法**——
所以主控看到 14 组 provider 之后，仍然不知道自己该用哪条路径派活。
（已修：`route` 现在会列出具名库、显示 `subagentModelSelection` 开关状态、并明确写
「派跨厂商红队用 `delegate(library_id=…)`；**绝不要**用 `longcat_worker` 当红队」。）

**两条坑必须记住**：

1. **`subagent(provider=…, model=…)` 会被拒**：
   `child LLM route "X/Y" is not allowed for this Session; without a recorded model-selection policy,
   explicit selection (including reasoning_effort) is limited to the parent route`
   —— 根因是 `@deepseek-ai/dsh-tool-subagent` 的 `subagentModelSelection` 配置**默认 `enabled: false`**，
   而 desktop profile 的 `cordis.patch.yml` 从未配过它。
   **但这不代表「没有其他 provider」**，只代表**不能显式指定**；具名库条目算「配置好的」而非
   「请求指定的」，**不受此限**。
2. **`longcat_worker` / `rb_lc25` / `rb_lc20` 三个工具的路由钉死 longcat**。
   拿它们当红队 = 拿同一个模型当所有角色 = 独立性为零，但输出里会写着「独立复核红队」。

**规则**：

1. **任何「环境缺少 X」的断言，必须同时给出「我试过哪几种获取方式」。**
   只报结论不报方法的缺席断言，一律按「未验证」处理。这条与 §10.14（把「我没复现」写成
   「未证实」）是同一条规则的两个面：一个关于数据，一个关于能力。
2. **看到「配置里有」之后，必须再问一句「我该怎么调用它」。**
   工具的清单视图（`route`）与调用视图（`delegate` / `subagent` / 具名库）是两回事，
   中间隔着一个 policy 开关——只知道前者会得出「有但用不了」的错误结论。
3. **`converge` 的「换过红队」判据必须以 `attack record` 记下的真实 provider/model 为依据，
   不许靠角色命名（"red"/"blue"/"devil"）推断。** 三个不同名字的角色可能是同一个模型。
4. **派活之前先看这个工具的路由是不是钉死的。**
   `route` 现在会打印具名库与 policy 状态；派完立刻 `attack record` 把真实路由落盘。

**这一条的代价**：四轮对抗的全部「独立性」声明都是假的，而它们已经写进了
`04-summary.md`、三份求助 MD、以及给用户的报告里。**机制没能发现，是因为机制从来没检查过
「攻击者到底是谁」——只检查了「有没有攻击记录」。**

### 10.18 第 18 类错误：派出去但失败的红队，账上不存在

**实测（2026-11-10，第一次真跨厂商派活）**：同一轮派了 3 个跨厂商红队——

| 库 | 路由 | 结果 |
| --- | --- | --- |
| `rb-red` | `agent2api-qoder/Kimi-K3.1-Pro` | **失败**（qoder 余额 0） |
| `rb-domain` | `agent2api-raccoon/sn-glm-5-3` | **失败**（运行中失败，无任何消息；同 provider 的 sn-kimi-k3 同轮成功，故非 provider 级故障） |
| `rb-devil` | `agent2api-raccoon/sn-kimi-k3` | **成功**，且给出六条高质量结构批评 |

**但 `red-attack.json` 里只留下成功的那一个。** `gate` 看到「1 个攻击者」，看不到「派了 3 个、挂了 2 个」，
**独立性被系统性高估**。而账上「我只派了一个」与「我派了三个但两个失灵」长得一模一样——
这两种处境完全不同：前者可能是资源不足，后者可能是上游临时故障，换个时段就通。

**修法**：新增 `attack fail <轮次> <provider> <model> <原因>`，写 `red-attack.json` 的 `failed[]`。
`gate` 放行前会打印：

```
NOTICE_ATTACK_FAILED: 另有 2 次派出失败 —— 独立性按**实际成功**的 1 个计，不按派出的 3 个计
```

**配套教训（同轮）**：PowerShell 5.1 的 `Set-Content -Encoding UTF8` **会加 BOM**，
而 `JSON.parse` 遇到 BOM 直接抛 `Unexpected token '﻿'`。工具里 **19 处** `JSON.parse(readFileSync(...))`
全部加了 `.replace(/^\uFEFF/, '')`。
凡是「读 JSON」都必须容忍 BOM —— 在本机这不是边缘情况，是常态。

**规则**：
1. **失败也要记账。** 任何「派出去」的动作，成功与失败都必须落到同一份账上；
   只记成功，等于把「尝试过几次」这件事从账上抹掉。
2. **独立性按实际成功数计，不按派出数计。** 派出 3 个成功 1 个 = 1 个独立来源。
3. **读 JSON 一律 strip BOM**，不要假设文件是自己写的就没 BOM（用户会用 PowerShell 改）。

### 10.19 红蓝队选模型：由工具决定，**不许问人**

**实测（2026-11-10，用户第 10 次强调后落成）**：主控在 R11–R14 四轮里全部用 `longcat_worker`
（路由钉死 `longcat/LongCat-2.5-Preview`）充当所有角色；被指出之后，又回头问用户
「rb-red 换成哪个」。用户原话：**「谁有余额就用谁，谁合适就用谁。我这不是这么多供应商吗？」**

用户的模型选择器里有 **16 个 provider、上百个模型**。而 `subagents\*.yaml` 是**纯文件**，
`delegate` 实时读目录，**新写一个立即生效、不用重启**。

**这件事不该由人决定，也不该由主控的记忆决定。已落成三个命令：**

| 命令 | 做什么 |
| --- | --- |
| `route probe [过滤词]` | 对每个 provider 的**倍率最低 2 个模型**实发一次最小请求（`max_tokens=16`），测出可用性与失败类型（`NO_BALANCE` / `FORBIDDEN` / `NO_MODEL` / `NETWORK`），写 `route-cache.json` |
| `route pick [偏好词]` | 按「**可用 + 积分倍率最低**」排序，直接给出推荐组合，并打印写库命令 |
| `route mklib <库名> <provider> <model> [描述]` | 生成 `subagents\*.yaml`，**立即生效** |

**标准流程（不要再问用户）**：

```
route probe          # 第一次 / 缓存超过一天时
route pick           # 看可用组合，倍率升序
route mklib rb-x <provider> <model>   # 写库
delegate(library_id="rb-x", prompt=…)
attack record <轮次> <provider> <model> <交付件> <角色>   # 记真实路由
```

**实测可用性（2026-11-10，本机）**：

| provider | 状态 | 证据 |
| --- | --- | --- |
| `agent2api-raccoon` | **可用** | `sensenova-6-8-flash` OK 2132ms；12 个模型横跨 Kimi / 智谱 / 商汤 / DeepSeek |
| `agent2api-qoder` | 余额 0 | 历史记录：qoder / qoder-intl / zcode 均额度为 0 |
| `agent2api-catpaw` | **余额不足** | 上游明确回复「当前余额不足以完成本次操作（credit.catpaw.meituan.com）」 |
| `agent2api-accio` | 不通 | `claude-opus-4-6` 与 `gemini-3-flash-preview` 同轮均启动即失败 |

部分模型在配置里标 **×0**（免费档），`route pick` 会把它们排在最前。

**规则**：

1. **派红队前先 probe**（缓存 24h 内可复用），再 pick，再 mklib。**禁止凭印象选模型。**
2. **禁止问用户"换哪个模型"** —— 那是一件写文件的事，不是决策题。
   用户已经说过 10 次以上。
3. **探测失败也要记账**（`attack fail`）—— 否则账上「只派了 1 个」与「派了 5 个挂了 4 个」长得一样。
4. **一个 provider 挂了不等于没有模型**：raccoon 一家就横跨四个模型厂商，
   足以凑出「不同厂商」的红队；真要跨 provider 时再 probe 其他家。

**这条经验的形状**：凡是被用户重复指出三次以上的事情，都不该留在"主控要记得"这一层——
必须落成命令、写进工具的输出、让下一次的人（或 agent）**不问也能做对**。

### 10.20 把「做项目的十几步」压成两条命令（2026-11-10）

用户的原话：**「我要的是当我做项目，能通过红蓝对抗不断磨合，把我的项目作品做出最好」**。

按这个标准，工具好不好不看它判据多不多，看**做一次项目要不要手工串十几条命令**。已补两处：

#### 1）`bundle` 现在自动附引文

原来 `bundle` 只打印「引用 N 处，最高 X/Y 行」，只说行号在范围内，不说那行是什么。
要核内容必须另外跑 `cite --quote`，而**本项目 14 轮一次都没跑过**——于是 S10 引用连续三轮
指向错行（说 Jan-1、实为 Jul-1）都没被发现。

现在每条 OK 之下直接打印该行原文：

```
OK  S10_midpoint_sensitivity.txt  引用 1 处，最高 6 / 7 行
     L4-6   Jan-1 (main),6.26,3.82,8.82,0.627,0.644 ⏎  ⏎ Jul-1 (midpoint),5.76,3.33,8.32,...
OK  S8_cohort_test.csv  引用 1 处，最高 1 / 4 行
     L1     grp,n,events,censored,median_lifespan_y,km_median_y,S_5y,S_3y,S_at_2019-07
```

**「核对内容」从「要专门跑一条命令」变成「默认就看见」。**

### 10.21 补上「做项目」最费手的三处（2026-11-11）

用户目标：**做项目时能通过红蓝对抗不断磨合，把作品做到最好**。按这个标准评估 15 个环节，
10 个够用、2 个勉强、**3 个是空的**——而且全在流程层，不在判据层：

| 环节 | 缺口 | 证据 | 已补 |
| --- | --- | --- | --- |
| 合并红队意见 | 无命令，每个项目手工写脚本 | `_lead_mkcases.mjs` 3,766 B | `merge` |
| 归档 | 无命令 | `_备份` 里 **127 个手工 zip** | `archive` |
| 项目配置 | 每次重报路径 | — | `project` |

#### `merge <轮次目录> <文件1> <文件2> … [--out=]`

把 N 份红队意见合成一份用例表：提取（容忍 4 种格式：`观点 N（…）` / 表格行 / `### N01` / `K01`）
→ 去重（同段落 + 判据正文 Jaccard ≥ 0.35）→ 按级别降序编号 → 合并来源（`A+B`）→ 出判重报告。

**验收时抓到一个它自测没覆盖的 bug**：PowerShell `Set-Content -Encoding UTF8` 给首行加 BOM，
而正则 `^\*\*观点` 对不上 BOM → **首条静默丢失**。已修（读文件时 strip BOM）并补回归自测。
> 教训同 §10.16：**BOM 这件事修了 19 处 JSON 读取，新写的代码照样踩**——凡读文件先 strip BOM。

#### `archive <源…> [--dest=] [--tag=] [--out=]`

一键打包 + 算 sha256 + **拒绝覆盖同名**（`return 2`，不是 `die`——`die` 是 `process.exit`，
会让上层 selftest 直接中断，实测 PASS 从 173 掉到 171）。Windows 走 `Compress-Archive`，Unix 走 `zip`。

#### `project set|use|list|show|unset`

项目配置存 `<DSH_HOME>\redblue-projects.json`：项目根 / 轮次根 / 期刊 / 备份目录。
以后不用每次重贴那一长串路径。

**现在做一次项目的完整链路（不再有手工临时脚本）**：

```
project use <项目>                 # 记住路径
spawn <靶件>                       # 出 3 份红队任务包 + 建库命令
delegate(library_id="rb-tech")     # 派出去
attack record / attack fail        # 成功与失败都记账
merge <轮次> <各份意见>             # 合并去重编号 → 01-cases.md
（蓝队改稿 → 复核 → 03-review.md）
bundle → audit → gate → adjudicate → converge
archive <轮次> --tag=<标记>         # 一键归档
```


### 10.22 跨厂商派活的真实成功率：**15%**（2026-11-11 实测）

**这是本项目最重要的一个环境限制数字，必须写在显眼处。**

两天里一共派了 **13 个跨厂商子代理**，从 `red-attack.json` 的账本统计：

| 轮次 | 成功 | 失败 | 成功率 |
| --- | --- | --- | --- |
| R14-1109cg | 1 | 8 | 11% |
| R15-111191 | 1 | 3 | 25% |
| **合计** | **2** | **11** | **15%** |

**失败模式高度一致：静默无消息。** 不是报错，不是余额不足，是「派出去了，然后就没了」——6 小时后既无 finished 也无 failed 通知，目录里也无产物落盘。

**最刺眼的一组对照**：

| 库 | provider / model | 结果 |
| --- | --- | --- |
| `rb-r15-domain` | raccoon / `sensenova-6-8-flash` | ✅ 成功，给出 8 条高质量方法审查 |
| `rb-r15-tech` | loomy / `spark-x2.6` | ❌ 静默失败 |
| `rb-r15-devil` | catpaw / `MiniMax-M3.1-Flash` | ❌ 静默失败 |
| `rb-r15-devil2` | raccoon / `sn-kimi-k3` | ❌ 静默失败（**同一组合在 R14 的 `rb-devil` 曾成功给出六条批评**） |

**而这两个失败的 provider 当时 `route probe` 都是通过的**（loomy 1407ms、catpaw 1900ms）。所以：

> **`route probe` 测的是网关能不能应一个 16-token 的请求，测不出「这个模型能不能当子代理干完一件活」。**

**由此得出的操作规则**：

1. **不要把「派了 N 个红队」当成「拿到了 N 份独立意见」。** 按 15% 算，派 3 个期望值是 0.45 份。
2. **派完立刻记账**，成功记 `attack record`，失败记 `attack fail`。**不记账 = 这笔账不存在**，而账不存在会导致独立性被高估（§10.18）。
3. **失败不要盲目重试同一组合**——已实测同组合一成一败（`sn-kimi-k3`），说明是间歇性的，重试有约 15% 的概率成功，但也可能再耗 6 小时。
4. **优先用「已经成功过的组合」**：本项目至今确定能出活的只有 `raccoon/sensenova-6-8-flash`（R15）、`raccoon/sn-kimi-k3`（R14）、`agent2api-autoclaw/glm-5.3`（R14 那次规则审计）。
5. **单份高质量意见 > 三份平庸意见。** R15 只拿到 1 份，但它给出 8 条、其中 2 条是真的新的（N22 的适用范围、N23 的 structural 越线）。**这比派 3 个都成功但都在重复历史更有价值。**

**这条数字的用途不是"劝退"，是让人在做计划时按真实概率算**：
如果你需要 3 份独立意见，按 15% 算要派出约 20 个——那就该先想清楚这值不值，
而不是派了 3 个、等了 6 小时、拿到 1 份，然后误以为"我已经做了三方交叉验证"。

```

**规则（硬性的）**：

### 10.24 引用数字的溯源规则

**论文里每一个数字，必须能指出算出它的脚本路径。**

```
论文写: log-rank χ²=14.79, p=0.0001 (P34c)
       ↑ 这个 (P34c) 必须真的能算出 14.79
```

**实测踩过的坑**：

| 数字 | 标注出处 | 实际情况 |
| --- | --- | --- |
| `χ²=14.79` | `(P34b)` | P34b 打印那行时 GBK 崩溃，**从未输出过 log-rank**（N16） |
| `χ²=3.31` | `(P34c)` | P34c 只算日历域；3.31 是**严格风险集口径**，算它的脚本未归档 |
| `χ²=1.665` | 无标注 | 同上，是标准方差口径，脚本未归档 |

**规则**：
1. **复算脚本必须归档**，不能只留复算结论。`03-review.md` 里有 `χ²=1.6651（标准方差）/1.7230（脚本方差）`，
   但算出它的脚本不在 `S11` 里——**这是存档缺口**。
2. **口径必须写明**。同一个量用不同方差公式会得不同 χ²（3.30 / 3.31 / 3.50 三个值都"对"），
   论文必须说清用的是哪个。
3. **指不出脚本的数字，不许写进论文。**

### 10.26 `spawn --retry=N`：把 15% 的成功率实际拉上去

**背景**：跨厂商派活的成功率实测只有 **15%**（13 派 2 成，见 §10.22）。派 3 个红队，期望值是 0.45 个成功。

**`--retry=N` 做的事**：一次生成 N 份任务包，**按 provider 去重轮换**，每份用不同的模型组合。主控依次派，某一份失败就换下一份。

```
node redblue.mjs spawn <靶件> --roles=tech,devil --retry=3 --out=<前缀>
```

生成 `<前缀>-1.md` / `<前缀>-2.md` / `<前缀>-3.md`，实测三份的分配：

| 份 | tech | devil |
| --- | --- | --- |
| 1 | loomy/spark-x2.6 (×0) | catpaw/MiniMax-M3.1-Flash (×0.05) |
| 2 | catpaw/MiniMax-M3.1-Flash (×0.05) | workbuddy/hy3-x (×0.05) |
| 3 | workbuddy/hy3-x (×0.05) | trae/deepseek-v4.1-flash-max (×0.06) |

**为什么按 provider 去重**：同一个 provider 下的不同模型不算跨厂商，独立性为零（§10.17）。

### 10.27 任务包附「靶件数字清单」

`spawn` 现在会读靶件，提取**所有带小数点的数字**，附在任务包里：

```
## 靶件里的数字（供核对）
红队质疑任何数字前，先跑 history 查它有没有被复算过。以下是靶件里出现的数字（前 60 个）：
  6.3, 0.55, 0.66, 0.0001, 3.31, 0.069, 42.0, 1.1, ... 14.79, 6.26, 6.25, 0.626, 0.546, 0.809, 0.664, ...
```

**为什么只保留带小数点的**：实测不过滤时，前 60 个数字里只有 8 个是统计量，其余是年份（2006/2026）、行号（172/162）、月份（08/07）——噪音会淹没真正的统计量。

**为什么这是必要的**：R15 的幻觉（把 `χ²=3.31` 当成不可复现）本质是「不知道这个数字有没有被复算过」。有了清单 + `history`，红队（和主控）能逐个核对。

`spawn` 会检查 `route-cache.json` 的时间。**超过 1 小时就报警**：

### 10.30 端到端验证：单元测试抓不到的四类问题（2026-11-11）

**背景**：发布前不光跑 selftest（178 条全过），还用**真实项目**（希腊课题 R14/R15）把完整流程跑了一遍。

| # | 问题 | 为什么 selftest 抓不到 | 后果 |
| --- | --- | --- | --- |
| 1 | `merge` 解析器不认 `**A1**` 格式 | 自测只造了 `观点 N`/`### N01`/`K01`/表格四种 | **整份红队意见漏掉**（22→29 条） |

### 10.31 R15 实战教训：机制侧（2026-11-11）

R15 是**第一次用完整链路跑真实项目**（32 条用例、3 个跨厂商红队、完整判定链）。
机制侧学到的：

#### 1. 复核红队也会静默失败 —— `--retry=N` 不是可选的

实测：复核红队第一个（loomy/spark-x2.6）**静默 45 分钟**，第二个（catpaw/MiniMax-M3.1-Flash）成功。
**规则：重要角色一律 `spawn --retry=3`，不要只派一个。**

#### 2. `03-review.md` 必须用标准 5 列格式

工具认的格式是：

```
| 编号 | 级别 | 状态 | 位置 | 判据与证据 |
| N01 | 严重 | 当前文本已答 | 文件:行号 | 证据 |
```

**主控自己写时踩过坑**：写成了 `| 编号 | 原判据 | 处置 | 复核判定 |` —— `gate`/`adjudicate`
都报 **0 条**（它们读第 2、3 列）。**写之前先看 `R14/03-review.md` 的表头。**

#### 3. `merge` 的格式覆盖靠 `MERGE_UNDERCOUNT` 兜底

本轮加了 `### 观点 N`（中文小标题）格式。**红队格式无穷无尽，不可能穷举** ——
解析器漏了格式时 `MERGE_UNDERCOUNT` 会报警（疑似数 vs 识别数 < 70%）。

**注意收紧**：纯数字编号列表项（`1. xxx`）要含严重度词才算疑似，
否则「已复算无误」清单会把疑似数抬高造成误报。

#### 4. `metrics` 中文按字计数

原实现只数拉丁词，中文文档（无空格）会被严重低估（实测 1572 B 的稿只数出 10 词）。
现已加 CJK 表意文字计数（每字一词，对齐「字数」惯例）→ 实测 10 → 334。

#### 5. 跨厂商红队最擅长「论证方向错」

R15 三条新缺陷：

| 编号 | 内容 | 类型 |
| --- | --- | --- |
| N30 | L144 删失方向写反（实际抬高 +0.026，不是压低） | 论证方向错 |
| N31 | 中点重锚反转队列方向，正文未披露 | 披露不全 |
| N32 | χ² 出处指向一个没有该列的文件 | 出处错 |

**都不是「数字算错」** —— 数字可以复算，方向和披露错了复算也发现不了。
**同模型红队 14 轮从未发现这类问题。**

#### 6. 补区间估计可能揭示被显著性掩盖的事实

N26 要求补效应量。补了 Greenwood CI 之后发现：
**5 年单时点的差值 95% CI 跨 0**（−0.357 到 0.122），
而 log-rank 的 p=0.0001 是**整条曲线**的检验。

**教训：显著性检验和单点估计回答的是不同的问题。** 只报 p 值会掩盖单点估计的不精确。
