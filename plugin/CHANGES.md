## M1 · 解析器两个静默错算（已修）

**触发**：R1 用例表有三张带"编号+级别"的表，`recount` 读出 `严重=10 合计=19`（真实 17 条）；`audit` 直接读出 `本轮用例数=0`。

**根因**：`STATUS_MAP` 缺 `已消除` 键，写成"已消除"时回落到级别列；解析器逐行匹配，不区分表，重复编号被重复计数。

**改动**：`STATUS_MAP` 补 `'已消除': '已消除'`；`recount` 增加重复编号探测，点名 `DUPLICATE_IDS: C01×2` 并 exit 2。

**验证**：
```
真实文件 recount：已消除=0/未结案一般=7  →  已消除=1/未结案一般=6（与手数一致）
自造重复件：DUPLICATE_IDS: C01×2，exitcode=2
```

## M4 · 新增 `metrics`（版面预算，只认实测）

**触发**：用户指出 JRP 上限 12 页。用 MiKTeX 真编译：**原稿 16 页、v3 17 页**。而此前按 500 词/页估算只有 11.04 页 —— 差了 5 页。

**改动**：`metrics <file> [上限] [实测页数]`。**只给估算绝不打 OK**；有上限无实测时报 `BUDGET_UNMEASURED`；有实测才判 `BUDGET_OK`/`BUDGET_OVER`。

## M9 · 新增 `quality`（红队质量统计机器化）

**触发**：三轮实跑里我算出的"红队判错 4 次 / 多报率 25%"**全靠人工手记**。这是判断"红队值不值得用、哪个模型好用"的核心指标，换个对话就丢了 —— 等于这项评估从来没做过。

**改动**：`quality <轮次目录...>`：从各轮 `03-review.md`（缺则回退 `01-cases.md`）算驳回率，分级别统计，多轮按编号合并、**后轮覆盖前轮**；并对「01-cases 里有、判定表里没有」的编号报 `UNMATCHED`（区分"本轮不审"与"彻底丢失"：只有历史轮次也没判定过的才算丢失）。

**验证（希腊课题三轮）**：
```
R1-1107g1  01-cases.md   17 条  驳回 3  17.6%
R2-1108h1  03-review.md  10 条  驳回 1  10.0%
R3-1108i1  03-review.md  11 条  驳回 1   9.1%
去重后（按编号取最新轮）: unique=21 rejected=4 rejected_rate=19.0%
  严重: claimed=9 rejected=1 rate=11.1%
  一般: claimed=12 rejected=3 rate=25.0%
```

**新命令反查出两个既有缺陷（都已修）**：

1. **`parseVerdict` 的「不成立」分支丢级别**。原代码 `claimedLevel: level`，而 `level` 此时已被映射成 `'不成立'` → 驳回行全落进"不成立"桶，按级别的驳回率永远显示 **0.0%**。修：保留原始级别列。不修的话，`quality` 的核心指标（严重级误报率）从第一天起就是假的。
2. 我自己在替换代码时**把 `casesPath` 的定义删掉了**（改一处断一处），靠 `--check` 与随后的实跑才发现。

**实测确认的已知盲区（不掩盖）**：机器只看到 4 次驳回，真实是 6 次。差的两条（F3 严重、F9 一般）在 R1 合并时被我写成了散文，从没进编号表。**因此严重级误报率的机器值 11.1% 是低估，真实约 22.2%。** 对应新增纪律见 SKILL §4.7 第八条：**被驳回的主张必须编号**。

**自测**：`selftest` 增 3 条（可解析单轮 / 「不成立」行保留原始级别 / 空目录 exit 2），`PASS=83 FAIL=0`。

## M10 · 模型级归因（`quality` 接入名册侧车）

**触发**：`quality` 只能算按级别的驳回率，算不了"哪个模型当红队命中率高"。而用例表的列是 `编号|级别|状态|E码|位置|判据|证据` —— **根本没有"谁提的"这一列**。归因链条（用例→角色→模型）只存在于 `04-summary` 的散文表里，机器读不到。按"有什么才能做什么"，不能编。

**第一次尝试失败（已回滚，如实记录）**：想给三张用例表加 `红队` 列。脚本只认第一个表头，而这三个文件都是**多表文档**（主表 + R2 追加表 + R3 追加表）→ 三轮的列数变成 10/11/12 混杂，表结构被改坏。**用上一次的课题备份 zip 把三张表原样还原**（9030/10281/10883 字节，红队列消失）。

**改设想**：改用**侧车文件**，对文档零侵入。

- 每轮独立 `redteam-roster.json`：`role → { provider, model }`（取自当时 `redblue_delegate` 的实际调用参数，非估计）
- `role-map.json`：`编号 → 角色`（依据各红队产物文件里的编号归属：tech 的 F1–F9、devil 的 DEV-01..05、domain 的 C-1..C6、N1–N3 出自 R2 复核红队、N4 出自 R3 复核红队）
- `quality` 合并所有轮次的名册与映射，输出按模型的 `claimed / rejected / rate`

**验证（希腊课题三轮，去重后）**：
```
agent2api-loomy/qwen3.8-flash             claimed= 9 rejected= 3 rate=33.3%
agent2api-raccoon/sn-sensenova-6-8-flash  claimed= 7 rejected= 0 rate= 0.0%
agent2api-raccoon/sn-kimi-k3              claimed= 5 rejected= 1 rate=20.0%
```
交叉核对一致：qwen3.8-flash = domain(C12–C17=6) + red-r2(N1–N3=3)，驳回 C15/C17/N2；sensenova = devil(C01–C06=6) + red-r3(N4=1)；kimi-k3 = tech(C07–C11=5)，驳回 C09。

**必须同时报的混淆因素**（已写进工具输出与 SKILL）：这份"按模型驳回率"**不是模型好坏排名**。sensenova 的 0% 全部来自 R3 复核轮（复核只需确认闭合，结构性上很难驳）；qwen3.8-flash 的 33.3% 拿的是领域/新颖性任务（那类主张本身最容易站不住）。**报数字必须同时报它被分到什么任务。**

**自测**：`selftest` 增 1 条（roster + role-map 齐备时归因链路不崩），`PASS=84 FAIL=0`。

**效率记录**：本轮我写错一处跨行单引号字符串（会语法错），`--check` 当场拦下，没有进到实跑。

## M11 · 新增 `canary`（测漏判 / 假阴性）

**触发**：R1–R3 只能测红队的**假阳性**（多报、判错，见 M9/M10），**假阴性（漏判）此前完全没有测量手段**。技能 §4.2 写了金丝雀办法，但一直是散文没有机器。

**改动**：`canary build <casesFile> <key.json> --ids ... [--anchors "C01=a|b;C02=c"]` 造识别锚键；`canary score <key.json> <redOutput.md>` 比对算召回率，召回 ≥50% exit 0、否则 exit 1。

**关键设计决定：canary 必须打未修复的原稿。** 拿已修好的 v3 去测召回是自欺——那些缺陷已不存在，红队找不到才是对的。本轮靶子定为 `manuscript_final.md`（指纹 `B30D0760`）。

**自动抽锚失败 → 改设想（手工锚）**：首次自动从中文判据里抽西文长串，7 条里 4 条只抽到 0–1 个锚（C04/C13/C14 为 0）。改为支持 `--anchors` 显式指定（每条 2–3 个），并把"自动抽锚不足"报成 `CANARY_WEAK` 明确告警。

**评分器先双向单测，再拿去量东西**：
```
干净假件（只提 4 条）→ 4/7，未提的 C05/C13/C14 各 0/3   ✅
完全无关输出        → 0/7，exit 1                        ✅
```

**可测试性修复**：`cmdCanaryBuild` 初版从全局 `process.argv` 读 `--ids/--anchors`，导致 selftest 无法传参（等于没有护栏）。改为从传入的参数数组读。

## M12 · canary 实跑标定：抓到「收敛 ≠ 覆盖」

**实跑**：`canary` 打**未修复原稿**（`B30D0760`），红队用 `minekuai/deepseek-v4.1-flash-1017`（本项目从未用过的独立 provider，零上下文、不知情）。

**评分**：4/7 = **57.1%** 召回（HIT：C01 C02 C03 C13；MISS：C04 C05 C14）。
首次评分报 3/7，是把 C13 判成 MISS —— **评分器自误判**：C13 的锚用了 `[12]`/`[13]`，那是**修复版**才有的编号，原稿不用方括号。改锚（`10.32942`/`9713570`）后 4/7。两份 key 都留档。

**锚设计教训（已写入 SKILL）**：锚要按「重新发现者会怎么写」选，不能按「修复后文本长什么样」选。后者等于抄答案。

**逐条裁决（全部回原文核对，不采信转述）**：9 条里 **7 条成立**（2 条严重：观点 6 = C01+C02+C03 的合体、观点 7 = C13）、**2 条不成立**（都是同一个错：把两个不同判据当成同一判据 —— S010306 有 stop time 且已被证明活跃，不是 never-active；Χανίων 判据是「2026 sampled-active」而非 anchor）。

**最重要发现：前三轮有真实漏判。** 9 条里 **5 条（观点 1/2/5/8/9）是 R1–R3 从未提出过的**：
- 删失约定自相矛盾（L59 说「无 stop 就删失到 2026-10-16」，L168 说这两个端点「recorded lifespan 1.0 y」）
- `161/164 reconciliation` 把 23 个「两路皆空」端点计入一致
- 结论 2 把「archival anchor」偷换成「reporting within 3 days」，而正文自己写「anchor proves the registry's last update, not that the sensor transmits now」
- KM 用日历表述（2012-09-28）却画在 duration 轴上
- Herfindahl 基线取「uniform 23-prefecture split」，而全文口径是 26 州（且 4 州零记录 ⇒ 22）

**机制结论（最重要的一条）**：`converge` 度量的是**同一批红队的复检稳定性**，不是**覆盖率**。R3 的「收敛」只证明那批红队不再报新问题；换一个模型立刻又多 5 条。技能第 647 行早已写这条规则，**主控违反了它** —— 这是"规则只写散文就会被违反"的第二次实证。

**落到机器**：

- `converge` 扫全部子目录的 `*.score.json`，打出 `RECALL_BASELINE: 57.1%`；找不到就报 `CONVERGE_NO_RECALL_BASELINE`
- 修了一处：`converge` 原先只扫「有效轮次」（有 `03-review.md`），而标定轮通常没有 review → 永远找不到召回证据。改为扫全部子目录

**自测**：`PASS=89 FAIL=0` 不变（canary 5 条已在 M11 补）。

## M13 · R5 建轮 + 三个工具缺陷（其中一个致命）

**R5 建轮**：把 R4 金丝雀新发现的 5 条编成 N5–N9，靶子 v3。先跑 `grep` 预验（不是推理）：6 个特征串在 v3 与**原稿**中的行号逐一相同（59/95/97/137/142/151/168/178/182/4），说明 v3 的改动全落在 L6/L21/L30 与 L189 之后，这段未被触碰 → **5 条全部未修，v3 不构成可投版本**。
`gate R5` 正确拦下：`致命=0 严重=1`（状态桶 `挂账=5` 下面藏着级别列的 1 条严重），判 `进下一轮`，exit 1。

### 缺陷 1（致命）：三态判定格式的整轮误读

`parseVerdict` 在「第 2 列是三态判定词」的分支里写的是 `level = parseLevel(m[3])` —— **把级别列当成了状态桶**，`STATUS_MAP` 根本没参与。后果：12 条「当前文本已答」被读成「一般=12、已消除=0」，`converge` 的干净轮数、`gate` 的闭合计数、`quality` 的驳回率全部失真。

**这条不是我读代码发现的，是 selftest 里两条 converge 用例把它逼出来的**（我改 shrink 判据后它们开始 FAIL）。修法：`STATUS_MAP` 提到分支外统一定义，三态分支改用 `level = STATUS_MAP[rawCell]`。

回归：`recount` 从「一般=12」变为「已消除=12」；希腊真实数据 `R3` 仍是 9/1/1、`R5` 仍是严重=1，未被误伤。

### 缺陷 2：「用例萎缩」判据选错了对象

旧判据是「条数 ≥ 上轮 × 0.9」，把「合法地只复核新发现」误报成"靠删用例收敛"（R5 实测：5 条 vs R3 的 11 条）。
真正要防的不是条数变少，而是**上一轮还没闭合的项在本轮静默消失**（已闭合的用例本来就不必再列）。
改判据后立刻抓到真事：**R3 未闭合的 N3(挂账) 在 R5 里消失** —— 说明我自己建 R5 时就丢了旧账。

### 缺陷 3：`converge` 与 `gate` 对同一批数据结论相反

## M15 · 修复「子代理不可续」——红蓝闭环从断开变为可用（最重要的一处）

**症状**：R6 执行手交的 6 块里有 3 块要打回，却**送不回去**。
- `send_message` 报 `active teammate "65f5aabf-…" not found`（它只认 Agent Teams 的 teammate，不认 subagent）
- `redblue_children` 只有 list / interrupt，没有继续

**错误的第一版实现**：我以为 `startActivation` 的 `childId?` 是续接句柄，于是用它"续"——宿主回
```
Error: subagent "65f5aabf-…" already exists
```
**那个 `childId` 是给新孩子预分配身份的，不是续接句柄。**

**查证方式**（不是猜）：用 `cordis_inspect_query` 拉 host `subagents` Service 契约，找到正确方法：

```
async sendMessage(sender: Agent, targetId: SessionId, content: ContentBlock[], options): Promise<MessageId>
"Steer one model-authored message to the sender's direct parent or direct continuous child.
 A running target admits it at the nearest step boundary; an idle target starts a turn,
 and an absent direct child cold-resumes from persistence."
```

**修复**：`redblue_children` 新增 `action: "continue"`（`child_id` + `prompt`），内部调 `ctx.subagents.sendMessage`，并保留"必须是本会话直接孩子"的授权检查（否则可以续到别人的会话上）。

**验证（决定性）**：
```
redblue_children {action:"continue", child_id:"65f5aabf-…", prompt:"打回 3 块…"}
→ {"continued":"65f5aabf-…","messageId":"eae28be3-c395-4492-9d7b-4f75398b1965"}
```
打回意见确实送达了原执行手 —— **红蓝的「打回—修正—复核」闭环因此从断开变为可用**。

**版本**：`@local/redblue-native` 1.0.0 → 1.0.1（加 continue，但 API 用错）→ **1.0.2**（改用 sendMessage）。每次改宿主侧插件都必须 `remove_bundle` + `install_bundle`，HMR 不重载宿主字节码。

**方法论教训**：接口不确定时，**去查服务契约**（`cordis_inspect_query` → `listService`），不要从字段名推断语义。我因为"`childId?` 看起来像续接"浪费了一轮实现和一次重装。

## M16 · 又两个误判 bug + 一个必须承认的结构性弱点

### bug 1：`gate` 把「裁决表」当成表外散落行（会让干净轮次永远不放行）

`scanStraySeverity` 只把含「逐条判定 / 判定表」的标题当作判定表区段，而**本技能模板自己用的标题就是「裁决表」**。
不匹配 → 整张判定表被当成"表外散落行" → 只要表里有级别为「严重/致命」的行，就误报 `STRAY` 并拦下。
实测 R6 全清（6/6 已消除）却被判 `不放行`，且只点名 N5 一条（因为只有它的级别 cell 恰好是「严重」）。

修：区段识别扩到 `逐条判定|判定表|裁决表|判定清单|裁决清单|逐条裁决|判定结果`。回归：R6 变 `放行`，R3 仍 `放行`，R5 仍 `进下一轮`。

### bug 2：`converge` 把"丢了又补回"永久判死

判据原来只看"上一轮未闭合项是否在本轮出现"。R3 的 N3 在 R5 消失（R5 建轮时的错），但 **R6 已经把 N3 作为必带旧账捡回来并修掉**。旧判据仍永久报 `SUSPICIOUS`，等于一条历史坏轮让整条链永不收敛 —— 那是惩罚已经改好的项目。

修：丢失的项若在**后续任何一轮**重新出现 ⇒ 记 `RECOVERED` 提示、不阻拦；只有"从未补回"才拦。R6 实测：
```
旧账补回 RECOVERED: R3-1108i1→R5-1108k1 丢了 N3，已在后续轮次补回（不按"靠遗忘收敛"处理）
CONVERGE: PASS (converged)
```

### 结构性弱点（如实登记，不是待办）

**`gate` 的"红队已攻击"检查是名义的。** 它只验证判定表里有红队归属列（`红队` / `来源`），**无法验证这个交付件真的被红队看过**。
本轮就是这个情形：v4 的独立复核连续 6 次派活失败（workbuddy-intl×2、catpaw/glm、codearts/pangu、minekuai、LongCat —— 后两者只写下 41/42 B 骨架就停），但 `gate` 依据 01-cases 里沿用的红队归属列，仍判 `attacked.ok` 通过。

**也就是说：四项全绿（gate 放行 / severity OK / reattack PASS / converge PASS）不等于"v4 通过了独立红队复核"。**
下一步该做的机制改动：要求每轮提供 `red-attack.json`，记录「哪个模型、在什么时间、审的是哪个**交付件指纹**」。没有它就不算 attacked。

## M17 · `converge` 的"连续干净轮数"名实不符（今天最危险的 bug）

**症状**：R8 有 1 条未闭合的**严重**项（N8：Figure 3 图注仍用日历日期表示 duration 轴交叉点），

**根因**：那一支只打印、**不中断循环**。

```js
if (clean) streak++
else if (openSevere || openFatal) { console.log(...) }   // ← 没有 break
else break
```

于是"连续干净轮数"实际数成了"历史上总共几个干净轮"。R2/R3/R6 三个**互不相邻**的干净轮凑成 3，
就满足了 `--n=2`。

**修**：非干净即 `streak = 0; break`，真正从末尾连续数。

**后果（必须写下来）**：今天此前所有"已收敛 / CONVERGE: PASS"的结论**都是基于这个 bug 得出的，全部作废**。
修后本课题的真实状态是 `连续干净轮数 = 0`，`CONVERGE: NOT_YET`。

**为什么自测没抓到**：`selftest` 里没有"末尾不干净、前面干净"的用例。已补一条
（R1/R2 干净、R3 有未闭合严重 → 必须 NOT_YET），`PASS=93→94`。

**这是今天第三次"指标名实不符"**：`quality` 的 claimedLevel（M9）、`gate` 的 attacked（M16）、
`converge` 的 streak（本条）。**一个名字说 A、实现算 B 的指标，比没有这个指标危险得多** —— 它会让人拿着假绿灯做决定。

## M34 · `occur draft`：先量再写，把"期望值"从猜变成实测

**起因**：上一轮我手写 spec 时把 `161/164` 的期望写成 3，实查是 4 处。

**命令**：`occur draft <稿件> [--out spec.json]`
扫描比率 / 倍数 / 百分比 / 小数 / 三位以上计数，按行去重计数，输出候选表并把**实测次数**直接写进 spec 的 `expect`。

### 过程中被自己的工具纠正三次

| # | 问题 | 真相 |
| --- | --- | --- |
| 1 | 第一版按"次数从少到多"排 | **排序帮了倒忙**：257 个一次性的 S(t) 数值把 `164`/`141` 全挤到后面。第 6 条纪律要抓的正是"同一说法出现在多处"，次数=1 的没价值 → 改为**从多到少** |

**第 3 条是真 bug**：`RegExp.test()` 带 `g` 标志是**有状态**的（会推进 `lastIndex`），

## M39 · 「过度纠正」也有护栏了：数字一变动就必须报出前后值

**为什么这类难防**：主控把**本来正确**的 Herfindahl 基线 `23 州 / 0.043 / 6.1×` 改成了 `26 州 / 0.0385 / 6.9×`。
改完之后**账仍然自洽**（1/26 = 0.0385 ✓、0.266/0.0385 = 6.9 ✓）——
所以 `ident`（账目闭合）查不出、`occur`（出现次数）查不出、任何"自洽性"检查都查不出。
**只有回原始数据重算分母**才知道 23 才是对的（23 = 至少有 1 起死亡的州数，1/23 = 0.0435 ≈ 0.043）。

**能机械化的那一半**：让"数字变了"这件事**无法悄悄发生**。
`apply` 每应用一块，就把 OLD/NEW 里的数字集合取出来比对，不同即打印：

```
APPLIED N22  (-78 +125)
  NOTICE_NUMERIC_CHANGE N22: 改动涉及数字  去掉[6.9, 0.0385, 26]  新增[6.1, 0.043, 23, 1]
  —— 数字变了就要能指出依据（回原始数据核，别只看账自不自洽）
```

**用历史败案回归验证**（把当时那两个块重放）：

| 块 | 通知 |
| --- | --- |
| N16（造数 `137/138`） | `去掉[137] 新增[3]` |
| N22（26 州 → 23 州） | `去掉[6.9, 0.0385, 26] 新增[6.1, 0.043, 23, 1]` |

**两次都会被当场标出**——正是我当时该警觉、却没有警觉的时刻。

**自测 +3 条**（能正常应用 / 通知被打印 / 通知里含前后数字）；`selftest 135 PASS / 0 FAIL`；
成功标记清单扩到 **13 个**（新增 `NOTICE_NUMERIC_CHANGE`）。

**局限要说清**：它只保证"数字变了会被看见"，**不保证"变得对"**。
判断一个数字该不该变，仍然只能回原始数据重算——这一步没有捷径。

`gate` 对"没绑指纹的攻击证据"只报 NOTICE（不拦，避免回溯判死历史轮次），于是 v13 是靠这条通过的。

否则 `CONVERGE_ATTACK_UNDECLARED` 直接阻断收敛。
**要求的是承认，不是掩盖**；没有候选稿文件的合成 fixture 不适用（无从指纹绑定）。

### 40.3 ★ 排序 bug：整晚报的「连续干净轮数 1 < 2」是假的

`dirs.sort()` 是字典序 → 轮次顺序成了 `R1, R10, R2, R3, …, R9`，**R10 被排到了第二位**，
于是 `converge` 把 **R9 当成"最新一轮"**，连续干净轮数自然算成 1。

**修法**：加自然序比较器 `natCmp`（数字段补零后比较），把 **4 处**排序全部改掉：

| 位置 | 原症状 |
| --- | --- |
| converge 的轮次排序 | R10 排到 R2 前 → 最新轮次认成 R9 |
| gate 的候选稿排序（可定位核对） | `v13` 排在 `v7` **前** → 取到 v7 的行号 |
| gate 的攻击指纹核对 | 同上 → **拿 v7 的指纹去核 v13** |
| 另一处 `rounds.sort()` | 同源 |

**修后实测**：`converge` → **`CONVERGE: PASS (converged)`**，且输出自证：
```
R8 状态桶干净但级别列有未闭合项（严重=1）→ 连续干净轮数在此中断
连续干净轮数 = 2（要求 ≥ 2）
旧账补回 RECOVERED: R3→R5 丢了 N3，已在后续轮次补回
```

**这是"名字排序不等于版本排序"这一类 bug**：代码没写错，是**把字符串序当成了时间序**。
和今晚第 4 类（量的范围划错）是同一家族——**都对，但都答错了问题**。

## M41 · `ident draft` 的往返缺陷：生成的 spec 自己都用不了

**这是"功能写完了但没验证往返"的典型**：M40 做完 `ident draft` 时，我只验证了"能写出骨架"，
**没有验证"骨架能被 `ident` 原样用起来"**。收尾时补测，当场发现 40 个候选里有 **2 个抽不出来**：

```
IDENT_VALUE_MISSING n161_164: 匹配不到 /ce reconciliation (\d+(?:\.\d+)?), of which 1/
IDENT_VALUE_MISSING n13_15:   匹配不到 /ght whose 2026-10-(\d+(?:\.\d+)?) anchors are/
```

**两个叠加的错**：

1. **比率不是数值。** `161/164`、`13/15` 被当成候选放进了 `values`，而 `ident` 抽值时会
   `Number("161/164")` = `NaN`。就算正则匹配上，也只会换个码报错。
2. **捕获组漏了比率那一半。** 生成的是 `(\d+(?:\.\d+)?)`，只覆盖 `161`，不覆盖 `/164`。
3. 附带：`ctx` 里的空白已被压成单个空格，正文里可能是多空格/制表符 —— 直接转义原文对不上。

**修法**：

- 候选里**排除含 `/` 的比率**（它不是数值，该由人手工拆成 `agree=161`、`total=164`）
- 空白一律用 `\s+` 匹配（`s.replace(/\s+/g,'\\s+')`）

**结果**：同一份 v13 上，`ident draft` → `ident` 往返从 **38/40** 变成 **40/40**，`IDENT_OK`、exit 0。

**回归测试 +4 条**（生成 spec / 比率不当候选 / 喂回不出现抽值失败 / 往返判定通过）。
`selftest 142 → 146 PASS / 0 FAIL`。

**教训**：一个"生成器"功能的验收标准不是"它输出了东西"，而是**"它输出的东西能被下游消费"**。
这和今晚第 7 类（判据没接线）是同一形状——**只看自己这一环通了，不算通。**

## M48 · R11 实跑抓到的机制致命缺陷：markdown 加粗让整行被静默丢弃

R11（真实红蓝对抗，不是探针）第一次把复核件写成合规格式后，立刻暴露了一个**致命级机制缺陷**。

### 48.1 现象

合并后的 `01-cases.md` 有 15 条：6 条严重（写成 `**严重**`）、7 条一般、2 条优化。但：

```
recount → 致命=0 严重=0 一般=7 优化=2 合计=9      ← 6 条严重不见了
gate    → 致命=0 严重=0 一般=7 优化=2 合计=9
          GATE_UNEXECUTED: 02-blue.md 不存在 …    ← 只靠这道拦住了
```

**如果 `02-blue.md` 存在，闸门会带着 6 条严重「放行」。**

### 48.2 根因

```js
function parseLevel(cell) {
  let s = String(cell).trim()                    // trim 只去空白，不去 `*`
  for (const lv of LEVELS) if (s.startsWith(lv)) return lv   // `**严重**`.startsWith('严重') === false
  return null                                    // → level=null → `if (!level) continue` 整行丢弃
}
```

`**严重**` 以 `*` 开头，`startsWith('严重')` 为假 → 返回 null → 该行被 `continue` 跳过。

**加粗是严重度列最自然的写法**，不是"格式不合规"。

### 48.3 为什么这次才暴露

- 历史 8 轮的复核件**全都没有合规引用**，`bundle` 一律 `UNDECIDABLE`，从没走到 `recount` 这一步
- 自测夹具用的都是裸词 `| C01 | 严重 | 已修 |`，**没有一条用加粗**
- 又一次「夹具与实现同源」（M45 记过同类：`ask` 的处置词表）

### 48.4 修法

新增 `stripMd()` 去掉首尾的 `* _ ~ \``，`parseLevel` 与 `strip` 都走它；新增 6 条自测覆盖
`**严重**`／`**致命**`／`` `一般` ``／`_优化_`／`**严重 → 已消除**`／`**严重** → 已消除`。

修后：`recount → 严重=6 合计=15`；`selftest 158 → 164 PASS / 0 FAIL`。

### 48.5 这是第五次同一类失效

| 版本 | 失效 | 方向 |
| --- | --- | --- |
| v5.4 | 不认 `R01` 编号（9 行只数出 4 行） | 少算 |
| v6.20 | 状态词吞掉级别列（致命全清零） | 少算 |
| v6.29j | 丢三态判定词（12 条读成一般=12） | 少算 |
| M45 | `ask` 处置词表不认同义词（10 轮 9 轮判 0 种） | 少算 |
| **M48** | **markdown 加粗整行丢弃** | **少算** |

**规律：解析器的失效方向永远是「少算」，从不是「报错」。** 而少算的结果是闸门按错误的低计数放行 ——
所以**凡「行数少于肉眼可见」必须当 bug 处理**（§10 已记，这次是又一次实证）。

## M49 · `reattack` 的编号撞车假阳性：20% 阈值太松

R11 收尾时 `reattack R10-1108r1 R11-1109cb` 报了两个**不存在的**问题：

```
假修复 FALSE_FIX = 1
  N16 上轮「已消除」(已消除) → 本轮「仍未解决」(挂账)
静默消失 DROPPED = 5
  N22 / N23 / N24 / N25 / N26 上轮「已消除」
REATTACK: FAIL (false_fix_detected)   exit=1
```

**但 R10 的 `N16` 是「137/138 造数已改」，R11 的 `N16` 是「P34b 引用错」——两件完全不同的事。**
N22–N26 也不是「静默消失」，而是 **R11 重新编号了**（这本身是 R11 的流程错误，`converge` 已经抓到并报了「靠遗忘收敛」）。

### 49.1 根因：阈值 20% 太松

```js
if (overlap < 0.2) { REATTACK_UNDECIDABLE … }
```

R10→R11 的共同编号 = 3/13 = **23%**，刚好过线，于是工具把**编号碰撞**当成了同一条用例在变化。

### 49.2 为什么 50% 才对

本机制规定「用例集只增不改」（SKILL §2 硬规则 5）。正常推进的两轮，后一轮应包含前一轮的全部编号，
**重合率应接近 100%**。低于一半就说明：要么换了对象，要么换了编号体系 —— 两种都必须先建编号映射表再判。

改成 `overlap < 0.5`，并把提示写完整（点明「新建轮次时重新编号」也是可能原因）。

### 49.3 顺手修了一条自测夹具（夹具不现实）

`reattack: 用例静默消失 → WARN` 的夹具是 **3 行 → 1 行（重合率 33%）**——
在新阈值下它（正确地）判 `UNDECIDABLE`，因为「3 条只剩 1 条」更像换对象而不是丢 2 条。

改成现实的「丢 1 条」场景（4 行 → 3 行，重合率 75%），并**新增一条**「重合率 0% → UNDECIDABLE」的断言。

### 49.4 结果

`selftest 164 → 165 PASS / 0 FAIL`；真项目 `reattack R10→R11` 现在 exit 2（UNDECIDABLE），
不再报假的 `FALSE_FIX`。

### 49.5 这条缺陷为什么重要

`reattack` 的整个存在意义是「让『已修』不再可信」。**它一旦产生假阳性，人就会开始忽略它的红。**
实测这次就差点让我在 `04-summary` 里写下「R11 有 1 条假修复」——而那条是编号碰撞。

## M50 · R13/R14 实跑：跨轮携带编号引发的一串解析缺陷

**症状链**（全部由"R12 原样携带 R10 的旧账"这一个动作撞出来）：

| # | 缺陷 | 性质 |
| --- | --- | --- |
| 1 | `parseVerdict` 的正则认不出 `R10-N17` 这种**跨轮携带编号** → `recount` 把 21 条只数出 17 条 | 少算 |
| 2 | `adjudicate` 有自己一套解析，同样不认；且级别只在 `m[3]`/`m[4]` 里找，`| 编号 | 级别 | 状态 |` 这个列序下级别在 `m[2]`，于是全判成「未标级别」 | 少算 + 判据失真 |
| 3 | `blueTeamExecuted` 的编号正则同样不认 | 少算 |
| 4 | `scanStraySeverity` 靠**标题词**（`逐条判定|判定表|裁决表`）判断"是否在判定表内"，而 R12 的标题是「复核红队**判定**」不含「判定表」三字 → 整张 21 行判定表被当成「表外散落」，6 条严重全被误报 STRAY | 假阳性，拦掉了干净的轮次 |
| 5 | `converge` 的「假修复」检查只按编号精确匹配 → R10 的 `N16`（137/138 造数已改）与 R11 的 `N16`（P34b 引用错）撞车，判成「上轮说修好、这轮又开」 | 假阳性 |
| 6 | `converge` 的「旧账补回」检查认不出带前缀的 `R10-N19` → R12 明明把 R10 的 N19/N20/N27 带回来并处置了，仍判「用例萎缩」 | 假阳性 |

**修法**：
- 编号正则统一支持「字母+数字 + 可选 `-字母+数字`」后缀（`R10-N17` / `R11-C03`）
- `scanStraySeverity` 改为**靠表头结构**判断（同时有「编号」列与「级别/判定/状态」列），不再靠标题词表
- `converge` 两处检查都改用「该轮编号」与「该轮前缀+该编号」两种形式匹配，**不做全局后缀归一**（不同轮同后缀可能是不同的事）
- `reattack` 与 `converge` 的重合率阈值统一提到 **50%**

**教训**：用词表判断结构，迟早会被同义词打败；用结构判断结构，才稳。

## M51 · `bundle` 把 `findFile` 的 ambiguous 结果当成"命中"

**症状**：作者按惯例把数据表备份成 `.bak` 后，`bundle` 报

```
OUT_OF_RANGE S10_midpoint_sensitivity.txt 引用到第 6 行，但文件只有 0 行 ([object Object])
```

**真因**：`findFile` 的 `shallowFind` 因路径深 4 层未命中，退化到 `fuzzyFind`，**同时命中 `.bak` 与真文件**，
返回 `{ ambiguous: [...] }` —— 一个**对象**。旧代码只判 `!p`（对象是 truthy），继续往下走，
`lineCount(p)` 里 `readFileSync(对象)` 抛异常 → `catch` 返回 **0** → 报出"文件只有 0 行"。

**要害**：它把**歧义**伪装成了**确定的数据损坏**（"0 行"）。

**修法**：ambiguous 时明确报 `AMBIGUOUS` 并列出所有候选路径，计入 `missing`，不再继续。

**教训**：`catch` 返回默认值（0 / [] / null）是所有"静默失真"的共同来源。
凡是 `catch { return 0 }` 的地方，都要问一句：**这个 0 会被下游读成"测出来是 0"吗？**

## M52 · `converge` 永远无法证明"换过红队"：新增机制外评审登记

**症状**：`converge` 硬要求「换过红队/换过模型」，而本机只有 `deepseek-account` 一个 provider。
所有轮次都是「同模型不同实例」，于是 `converge` 在这台机器上**物理上永远 PASS 不了**。
