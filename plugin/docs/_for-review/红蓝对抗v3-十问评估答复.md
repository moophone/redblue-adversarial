# 红蓝对抗 v3 评估答复

> 格式：结论 → 依据 → 可操作建议。标注【事实】= 有实测/文件证据；【判断】= 我的推断；【不确定】= 样本不足。
> 除引用三份送审文件外，我在本机把 `01` 里的八个脚本抽出实跑过，并独立跑过一轮 v2 机制（第 3 个样本）。

## 先说四个实测发现（都是事实，附命令输出）

**F1【事实】`recount.sh` 认不出「一般 / 优化 / 已消除」，而它是 v3 的硬要求脚本。**
根因：`sub(/[（(].*/,"",lvl)`（01 文件 769 行）在 mawk 下按**字节**匹配字符类，全角`（`= `E3 80 88`，而「消」的末字节、`般`「优」里恰好含同类字节，于是级别词被截断：

```
$ for w in 致命 严重 一般 优化 已消除; do ...; done
致命 : OK        严重 : OK
一般 : CORRUPTED->一�     优化 : CORRUPTED->�     已消除 : CORRUPTED->已�
$ ./recount.sh t.md      # 3 条：已消除/一般（残留）/优化
致命=0 严重=0 一般=0 优化=0 已消除=0 未识别=3
```
后果不是"计数偏差"这么轻：§11 规定"与红队自报不一致时**以脚本为准**并记挂账"，而「已消除」是放行的主力（02 第二次实跑 17/18 属实）。于是**每轮必然产生假挂账，且主控若真按"以脚本为准"，会把已消除当 0**。
修法：别用正则删括号，改前缀锚定 `lvl ~ /^致命|^严重|^一般|^优化|^已消除/`。我已验证：同一样本从 3 条未识别变为 3 条全对。同时脚本应加"未识别 > 0 → exit 1"。

**F2【事实】`audit_count.sh` 不认 N 系列，「只减不增」在 R2/R3 完全失效。**
§5.3 规定新增用例编号 `N01/N02`，但脚本只匹配 `^\| C[0-9]{2} \|`：

```
$ ./audit_count.sh R2 R1    # R2 比 R1 多 N02、N03
本轮用例数: 2   上一轮: 2   COUNT_OK     exit=0
```
新增 2 条未被检出（`recount.sh` 用 `C|N`，两个脚本口径不一致）。修法：正则改 `^\| (C|N)[0-9]{2} \|`。

**F3【事实】`check_contract.sh` 与 §5.3/§10 自相矛盾。**
§5.3 与 §10 目录树注明 R2「`01-cases.md` 不重复建」，但契约校验要求五件产物齐全：
```
$ ./check_contract.sh rounds/R2-1031a3
CONTRACT_VIOLATION: missing 01-cases.md
```
照设计跑 R2，契约校验**必然失败**。另外 §5.1 开工 5 步里没有"建 `fingerprints/`"，而 `check_gate.sh` 要求它存在（实测 `STATE_NOT_INITIALIZED: fingerprints/ missing`）。

**F4【事实】唯一造成过整天重跑的真实故障，v3 的 11 条改动里没有对应修复。**
02 第 32 行明确要求"协议里必须规定重试写不同文件名 / 落盘后立刻转存"。但 §2 自动化契约只写"子代理失败/超时 → 自动重试 1 次"，全文件 grep "不同文件名|转存" 无命中。

> 这四个集中于**脚本与流程的确定性部分**——恰恰是设计里打算下沉为"可机械执行"的那一层。这不是偶然，见 Q7/Q10。

## Q1 独立性怎么补

**结论**：实际增益排序 = **跨模型 ≫ 零上下文派工 > 红队不写文件**（后者增益接近 0，见 Q2）。

**依据**：三个手段防的东西不同。跨模型换的是**世界观**（唯一能真正打破"同一模型自己审自己"的手段，02 §5 列为未验证项）；零上下文派工换的是**锚定**（不给验收标准，红队自己抽"它声称了什么"，能少受主控框定）；红队不写文件防的是**篡改**——而这个风险实测零发生（见 Q2）。

**建议**：① 跨模型只换**红队**一方，蓝队留原模型，保证修复质量不降；② 零上下文派工作为默认，主控只给"交付件路径 + 六个维度 + 判据表"，**不给验收标准、不给用例示例**；③ 补充你没列的：**基准召回**——用历史已确认缺陷（如 02 的全二次基反例 C02）做回归，每轮看红队能否独立重现，这是唯一能**量化**独立性的办法。

【判断】②③ 组合起来，成本远低于跨模型，且可测量。【不确定】跨模型在本 harness 是否真能指定 provider，未核实。

## Q2 红队不写文件是否可行

**结论**：**不建议**。它防的风险实测零发生，代价却是真实的。

**依据**：我独立跑的那一轮，四个指纹校验点全部 `FP_MATCH`；02 两次实跑里，"红队改交付件"也从未发生。**三次样本、零命中**。但真实的写事故发生过一次——不是改交付件，是**迟到子代理覆盖了红队自己的产物**（02 第 30 行）。所以写风险确实存在，只是方向不同。

**建议**：把防御成本从"防篡改"转到"防覆盖"：① 重试实例写 `01-cases.r2.md`，落盘后由主控转存为正式名（补 F4）；② 四校验点合并为**收尾时校验一次**（零命中意味着中间三次是纯开销）；③ 保留红队写文件（长用例表受输出长度限制，且失败可恢复、署名可追溯）。

## Q3 闸门要不要加覆盖度

**结论**：要加，但**绝不能由红队自报**——自己评自己覆盖，等于没有。

**依据**：02 §4.3 已经指出"现有未覆盖范围是主控写的，不是红队申报的"。但换成红队申报只是把无依据换成另一种无依据。

**建议**：改**维度清单驱动**——主控在 `00-target.md` 给固定清单（六个通用维度 + 类型专属：统计前提 / 伦理合规 / 引用完整性），红队对每个维度必须填"覆盖 / 不适用 / 未覆盖"，且"覆盖"必须带 ≥1 个具体检查点指针。防虚报靠两处交叉：① 让**蓝队反向申报**"我修的问题属于哪些维度"，与红队申报做差集——红队说没覆盖伦理却修了伦理问题，即为虚报；② 基准召回（Q1③）。

## Q4 "可复算覆盖率"当硬准入会不会误伤

**结论**：会。这条线不该划在"能否**执行**"，该划在"能否**证伪**"。

**依据**：论证逻辑断裂、伦理问题确实跑不出结果，但它们可以被证伪——只要能构造出一个读者一步就能核验的矛盾。

**建议**：把"可执行验证"扩成三类，任一即可立致命/严重：① 命令复算（给命令+输出）；② **最小可运行反例**（02 的 C02 全二次基反例就是典型，它不需要原环境）；③ **同文档内两个引用的直接矛盾**（给 A 行号与 B 行号，矛盾自明）。真正无法证伪的（写作质量、伦理取向）单列为**判断类**，不进闸门，直接进"给人看的清单"。

## Q5 红队自己漏判，谁来补

**结论**：靠**基准召回**校准，而不是靠加一个审红队的角色。

**依据**：红队有"过度升级"动机（多抓显得有价值），蓝队有"过度降级"动机（少修省事）。两者偏差方向相反，所以现有的红蓝双向已经能压住**误判为高**的一侧，压不住**漏判为低**的一侧。加第三方抽检，等于再加一层有同样盲区的模型。

**建议**：① 每轮固定抽 3 条红队判为"一般/优化"的，由主控（或复核红队）做定向复判，输出"维持/升级"，成本极低；② 建立历史缺陷基准集，每轮跑召回率，低于阈值就在 04 里标"本轮红队质量存疑"；③ **不建议红蓝互换**——互换换的是立场，不换动机偏差。

## Q6 串行能不能并行

**结论**：按维度拆红队**不值得**（会漏跨维度问题）；值得做的是**同一环节冗余**。

**依据**：02 教训 #2——同一模型同一交付件，一次 12 条只抓到软问题，一次 18 条抓到推翻核心主张的硬反例。**红队质量方差才是主要矛盾，不是 40 分钟**。

**建议**：派 2 个独立红队、同输入、各自造用例，主控取并集（去重后可能超 20 条，那就把上限提到 30）。这比"拆分省时间"更对症：它换的是覆盖，不是速度。至于时间——真要省，应该砍的是空转部分（见 Q10），不是加并行。

## Q7 插件还是 skill，边界在哪

**结论**：判定标准一句话——**该步骤的正确结果是否唯一、且能否在不理解交付件语义的前提下判定**。是 → 下沉插件；否 → 留 skill。

**依据**：按这个标准，现有的 8 个脚本归类是对的。但 F1–F4 说明**下沉得还不够彻底**，也说明下沉部分一旦写错，危害大于留在 skill 里（因为脚本有权威感："以脚本为准"）。

**建议**：还应下沉——闸门算术（致命/严重计数 → 结论）、未修编号集合比较、覆盖度统计、挂账上限检查。**不应**下沉——严重度判定、"已修是否属实"判定、目标抽取。另加一条硬规矩：**任何被赋予"以其输出为准"的脚本，必须自带自检用例**（F1 若有 5 行样例测试就不会上线）。

## Q8 可视化优先级

**结论**：**C（对话内三方对照表）≫ A（任务板）> B（侧边栏）**。

**依据**：对结论质量的贡献来自"让人看到红蓝分歧"。三方对照表（用例 × 红队判级 × 蓝队处置 × 复核结论 × 实跑证据）把分歧直接摊给人——而**人是这套机制里唯一的外部真值**（你自己承认闸门无外部真值）。A 显示的是"谁在跑、跑到哪"，解决的是 02 §4.6"过程不可见"的体验抱怨，对结论正确性贡献≈0；B 开发量大且状态刷新即丢失。

**建议**：先做 C，做成**每轮末自动输出一张表**，并且只列有分歧的条目（一致的不占版面）。

## Q9 定位：多轮评审 还是 证据收集

**结论**：**证据收集流程**。只留一个就留**强制可复算**。

**依据**：02 说"抓到问题的几乎全是跑一遍就露馅的，没有一条是靠多审几轮审出来的"。我那一轮独立印证了，并补一个关键区分：抓出 8 条"已修"不属实的是 **R1 内的复核红队（实跑验证）**，不是多轮——**R2/R3 至今一次没真跑过**。所以最小有效核是「造 → 修 → 实跑复核」，多轮是未验证的附加层。

**建议**：把 R2/R3 从"默认流程"降为"可选"；把"复核必须实跑命令/重读文件"从角色卡上升为**硬准入**（无实跑证据的复核结论不计入闸门）。

## Q10 最狠的一问

**结论**：方向没错，但**"自动闸门"这个部件是错的**，而且它吃掉了 90% 的复杂度。

**依据**：你的判断（02 §4 末）——90% 复杂度在流程正确性、10% 在结论正确性，而抓到问题的全在 10%——我这一轮**独立复现了**：四个指纹校验点零命中，契约/门禁脚本本身反倒贡献了 4 个 bug（F1–F4）。一个防御零发生风险的机制，同时自己成为缺陷来源，这是净负收益。更根本的是：闸门无外部真值时，"致命=0 且严重=0 → 放行"本质是**用形式合规替代实质正确**。

**建议**：闸门从"自动放行器"降级为"**未决清单 + 人工签字位**"：① 砍掉 R2/R3 与四校验点中的三次（收尾校验一次即可）；② 删掉挂账上限公式这类自纠过一次的规则（每加一条流程规则就多一个 bug，你自己已验证两轮）；③ 省下的复杂度投到三处：每个致命/严重绑定可证伪验证（Q4）、维度清单驱动覆盖（Q3）、三方对照表给人签字（Q8）。

**替代方案一句话**：它不该是一条"自动判定流水线"，而应该是一台**分歧制造机 + 证据收集器**——产出给人的，不是结论，是"红队这么说、蓝队那么说、实跑结果是这样"的对照表和三条未决项。判定权交回人。

【判断】以上关于"该砍什么"的判断基于 3 个样本（你 2 次 + 我 1 次），且都是同一交付件类型。【不确定】换到代码/数据集类交付件上，"复核实跑"的收益是否同样占主导，未验证。
