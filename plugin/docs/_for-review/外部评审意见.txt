## v2 仍存在的局限（实事求是）

### 1. 同模型自审的天花板未突破

红蓝双方仍是同一权重、同一训练分布的模型。v2 文档自己也承认了这一点，给出 `longcat_worker` 跨模型方案作为可选增强，但不是默认配置。这是**原理性局限**，不是协议设计能完全解决的。

### 2. 文件契约本质未变，无硬强制力

所有规则靠模型自觉遵守。跳过步骤、少写产物、私自放宽闸门，没有机制层面的拦截。指纹校验只能**事后发现**红队篡改交付件，不能**事前阻止**。

### 3. 闸门缺乏外部真值

严重度标签仍由模型自贴，零确认设计意味着无人复核。一次误判的 "放行" 会静默交付。这是设计取舍（换不中断），但风险客观存在。

### 4. 子代理的 token 成本被低估

每个子代理都是全新上下文，每轮都要重新读取交付件、角色卡、前序产物。三轮跑下来，总 token 消耗未必低于跨会话方案，只是用户操作成本降了。

### 5. 红队停止规则仍偏软

20 条上限是数量约束，没有质量收敛规则。理论上红队可以把 20 条全标 "严重"，蓝队必须逐条处置，成本仍可被单方面放大。

### 6. 挂账机制缺乏约束

"挂账" 是蓝队的合法选项，但协议未规定挂账的上限比例和审批规则。如果蓝队把严重问题大量挂账，闸门统计会失真。

## 可落地的优化建议

### 高优先级（改动小、收益大）

1. **增加挂账比例硬约束**：单轮挂账不得超过严重及以上问题的 30%，超过则闸门自动判 "进下一轮"，防止用挂账冲抵严重问题。
2. **严重度降级强制留痕**：红队判定时若预估严重度与最终判定不一致，必须写明降级理由，避免随意降档凑放行条件。
3. **子代理输入裁剪**：派红队时只给交付件 + 角色卡，不给协议全文；派蓝队时只给用例 + 交付件，减少冗余 token。

### 中优先级（结构性优化）

4. **引入 "盲审" 模式**：第一轮红队造用例时，不告知蓝队身份和修改历史，纯黑盒评审，减少锚定偏差。
5. **增加一致性校验**：第 3 轮派第二个独立红队子代理复核闸门结论，两害相权取其轻，用额外 token 换放行可靠性。
6. **产物自动校验脚本**：写一个简单的格式校验脚本，检查四份产物是否齐全、表格列数是否对、严重度标签是否规范，用机器检查替代人工核对。

### 低优先级（增强项）

7. **跨模型配置标准化**：把 longcat_worker 作为红队默认选项做成一键开关，明确跨模型与同模型的闸门标准差异。
8. **历史问题库积累**：每轮结束后把真实命中的严重 / 致命问题沉淀成 checklist，红队首轮先过 checklist 再发散，提升评审效率。
