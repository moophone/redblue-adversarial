# 红蓝对抗：问题清单

> 这份文件只写**查到的**和**能验证的**。凡是推测，我都标了「判断」。
> **我没有实际跑过一轮完整的红蓝对抗**，所以涉及"跑起来会怎样"的部分都是判断，不是实测。

## 1. 现状（事实）

1. 它是**文件契约**，不是可执行机制。产物区 `接入卡.md` 原话：
   > 这套机制是**文件契约**，不是后台服务。它不会"运行"，只有被某个会话读进来并照着做才生效。
2. **要求跨会话**：技能写明"红蓝两方不可由同一会话兼任"；`接入卡.md` 整篇在讲"在别的会话里用"。
3. 角色三个：**红队**（只评审、不改交付件）、**蓝队**（执行 + 自证）、**主控**（定目标、仲裁、判放行）。
4. 产物四件：`01-cases.md`（红造用例）→ `02-blue.md`（蓝逐条处置）→ `03-review.md`（红逐条判定）→ `04-summary.md`（主控复盘 + 闸门）。
5. 闸门：**致命 = 0 且 严重 = 0 → 放行**；最多 3 轮。
6. **零确认**：主控不向人提问；第 3 轮未过即 `GATE: BLOCKED` 照常交付。
7. 证据纪律：引用必须指到 文件 + 行号 / 命令 + 可复现输出 / 数据源；蓝队判"不成立"必须附反证。
8. 硬安全约束 5 条（不越目录、不删改权限、不诱导安全绕过、被拦截就换可复算路径、不做话术攻击）。
9. 已有 R1~R3 真实产物 —— 说明这套流程**跑通过**，不是纸面设计。

## 2. 问题清单

### P1 多会话要求与"快速把关"的目的相悖
- **事实**：技能与接入卡都要求红、蓝、主控分属不同会话。
- **后果**：要用一次，得开 2~3 个会话、手工传递交付件路径、靠文件在会话间接力。
- **判断**：对"交付前快速把关"这个用途，摩擦远大于收益。

### P2 多会话其实不必要 —— 子代理已经提供"不同上下文"
- **事实**（来自本 harness 自己的工具定义）：
  - `subagent`：*"a separate agent that works in its own context"*，其任务说明 *"does not share this conversation's context"*。
  - `subagent_fork`：*"inherits this conversation: a child agent seeded with all completed turns so far"*。
  - 你自己的 `longcat-worker` 技能里也写着：worker"是全新子代理，看不到这条对话的任何内容"。
- **判断**：旧设计要的"审查者与作者不是同一个上下文"，**用 `subagent` 在一个对话里就能拿到**。跨会话是多余的。

### P3 同一个模型自己审自己
- **事实**：红队和蓝队跑在同一个模型上（会话用什么模型，双方就用什么）。`接入卡.md` 里提到另一条路是"用 longcat_worker 派给 LongCat"。
- **判断**：同权重、同训练分布的模型互审，发现问题的能力弱于跨模型 / 跨人。这是这类方法固有的天花板，不是这份协议的错。

### P4 纯文件契约，没有任何强制力
- **事实**：见第 1 条第 1 点。协议靠模型自愿遵守。
- **后果**：跳过步骤、少写产物、闸门判错，都没有东西拦得住。

### P5 闸门没有外部真值
- **事实**：致命 / 严重 是红队自己贴的标签；零确认意味着没有人复核。
- **后果**：一次错误的"放行"会被静默交付。唯一的兜底是第 3 轮的 `GATE: BLOCKED`。

### P6 轮次可能空转
- **事实**：`01-cases.md` 每轮由红队**重新生成**；协议没有限制每轮用例数量，也没有禁止后续轮次提出新用例。
- **后果**：红队可以每轮造出新的"严重"项，蓝队永远修不完 → 3 轮上限到了还没收敛。

### P7 没有"能复算就复算"的硬要求
- **事实**：证据纪律只要求"指到路径 + 行号 / 命令 + 输出"，没有要求**重跑**计算。
- **判断**：对科研交付件（论文、数据、脚本），重跑复算是价值最高的检查，现在只是可选项。

### P8 严重度没有按交付件类型定义
- **事实**：致命 / 严重 / 一般 / 优化 是通用四级，没有针对"论文 / 数据集 / 代码"给出判据。
- **后果**：不同人、不同轮次对"严重"的理解不一致，闸门不可比。

### P9 产物在会话之外
- **事实**：产物是共享目录下的 markdown；会话里看不到推理过程。
- **后果**：用户在界面上看不到红蓝双方到底在吵什么；跨会话搬运靠手工。

### P10 上下文成本高
- **事实**：技能正文约 14.6 KB，加上 protocol、两张角色卡、四份模板，每个参与会话都要装一遍。
- **判断**：对"快速把关"来说偏贵。

### P11 并发写 `state.md` 会撞
- **事实**：协议自己列了这张表（轮次目录同名互撞 / state.md 同时写会覆盖 / 同一交付件两个蓝队同时改）。
- **后果**：靠约定缓解，没有锁。

### P12 红队没有停止规则
- **事实**：唯一的刹车是"禁止无依据抬杠"。
- **后果**：用例可能过多，蓝队必须逐条处置，成本被放大。

## 3. 哪些地方是好的（实事求是）

- **证据纪律**（路径 + 行号 / 命令 + 输出 / 数据源）—— 这类机制里最值钱的部分。
- **"不成立必须附反证"** —— 防止蓝队一句话否掉问题。
- **硬安全约束 5 条** —— 边界清楚，且明确禁止绕过审批层。
- **零确认原则** —— 符合"别老打断我"的偏好。
- **3 轮上限** —— 至少不会无限循环。
- **已有 R1~R3 真实产物** —— 流程跑通过。
