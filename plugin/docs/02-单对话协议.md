## 2. 自动化契约（v3 核心）

**主控在整轮运行中不得向用户提问、不得等待确认、不得要求选择。** 所有判断由主控按本协议自行做出，并写入 `04-summary.md` 的「主控决策」节。

具体规则：

| 场景 | 主控怎么办（不提问） |
| --- | --- |
| 交付件类型不明确 | 按 §7 的**分派算法**自动归类；两类都沾边就选覆盖面更严的那类，并在 04 里写明理由 |
| 验收标准没给 | 从交付件的**自身主张**反推：逐条抽出"它声称了什么"，每条一个验收点，写进 `00-target.md` |
| 边界外没给 | 默认边界外 = 与交付件无关的一切；在 00 里列"本轮不审什么" |
| 严重度拿不准 | 按 §7 判据表取**更严重**的一档，并在判定里写"取严理由" |
| 红蓝结论冲突 | 不裁决谁对，把两方证据并列写进 03/04；闸门按 §6 机械执行 |
| 闸门未放行 | 自动进下一轮（≤3 轮），不问 |
| 第 3 轮仍未放行 | 自动 `GATE: BLOCKED`，照常交付并写明原因，不问 |
| 挂账超上限 | 自动判"进下一轮"，不问 |
| 子代理失败/超时 | 自动重试 1 次。**重试实例必须写不同文件名**（如 `01-cases.r2.md`），落盘后由主控转存为正式名——实测有过原实例迟到 50 分钟、覆盖重试实例产物、导致整天重跑的故障（v3.3 修，F4）。仍失败则记 `BLOCKED: subagent-failed` 并继续下一可用步骤，不问 |
| 发现交付件有安全风险（硬安全约束） | **唯一例外**：停下，写 `BLOCKED: safety`，把事实交给用户 |

**主控必须记录决策**：`04-summary.md` 里「主控决策」表格，每行 = 决策点 + 选择 + 理由（一句话）。

## 4. 为什么一个对话就够

本 harness 的 `subagent` 定义：*a separate agent that works in its own context … does not share this conversation's context*。
`subagent_fork` 则是 *inherits this conversation: a child agent seeded with all completed turns so far*。

**要独立性用 `subagent`，不要用 `subagent_fork`。**

> **诚实边界**：这是"弱独立"——主控仍会把目标、验收标准、红队用例喂给下一方，世界观由主控框定。真正的多样性只能靠换模型（见 §13）。

## 5. 流程

### 5.1 开工（主控，不派子代理）

1. **定目标**：按 §2 自动推导——抽交付件自身主张 → 每条一个验收点 → 写 `00-target.md`。
2. **定类型**：按 §7 分派算法归类，写进 00。
3. **取基线指纹**：`node tools/redblue.mjs init <roundDir> <交付件...>` —— 一次完成建目录 + 写 `fingerprints/00-baseline.txt`（文件清单 + SHA256）。
   > v3.3 起**不再用 bash 脚本**：目标机器没有 bash/awk/grep，v3 的 8 个脚本一次都跑不起来；且 mawk 在 C locale 下按字节匹配 `[（(]`，会把「一般/优化/已消除」截断成未识别。改用 Node 单文件工具，自带 `selftest`。
4. **建目录**：由 `init` 完成（`rounds/R{轮次}-{MMDD}{2位}/` + `fingerprints/`）。
5. **写 `current.json`**：`{round, shortcode, stage, baseline, deliverable_type}`（可覆写）。
6. **`state.md` 暂不写**（只在闸门后追加，见 §10）。

### 5.2 R1（红 → 蓝 → 红 → 主控）

| 步 | 谁 | 输入 | 输出 |
| --- | --- | --- | --- |

| R1-a2 | **领域审稿人** `subagent`（与 a1 不同模型优先） | 交付件 + **目标期刊/赛事的显式要求** + 文献检索（arxiv / semantic-scholar / openalex） | `01-cases-domain.md`（≤6 条） |
| R1-a3 | **魔鬼代言人** `subagent` | **只给交付件**。不给维度、不给判据、不给目标、不给边界外 | `01-cases-devil.md`（≤5 条） |
| R1-a4 | 主控 | 三份合并去重 → 统一编号（冲突保留两方措辞） | `01-cases.md` |

**为什么拆三张脸（v4 核心）**

三轮实跑的红队**全是技术审查员**，所以抓到的 100% 是局部事实错误（行号、算术、量纲、口径），**没有一条**是"这个研究问题不成立""这个结论早有更好版本"。同一个模型审同一个模型，只能看见自己能想到的缺陷类型。

| 角色 | 它查什么 | 关键 |
| --- | --- | --- |
| 技术审查员 | 写出来的对不对 | 现有职责 |
| 领域审稿人 | 值不值得写、方法被接受吗 | **必须接外部**（文献、期刊要求），否则无从判断 |
| 魔鬼代言人 | 这篇根本不该做的理由 | **必须什么都不给**——给维度就等于给框 |

三者**可并行**（互不依赖），总耗时 ≈ 单个最长者。

**模型：按角色钉死，随时可换（v6，换掉 v5 的 headless 方案）**

**机制**：`dsh-subagent-library` 维护一份**具名子代理名册**，一个角色一个 YAML，`provider` / `model` 写在文件里。

```
<DSH_HOME>\subagents\
  rb-red.yaml     # 红队：provider=longcat / model=LongCat-2.5-Preview
  rb-blue.yaml    # 蓝队：provider=spark   / model=spark-x2.6
  _backups\
```

主控用 `delegate({ library_id: "rb-red" | "rb-blue", prompt })` 派活。

**为什么换掉 v5 的 headless 方案（v5 已实测跑通但被淘汰）**：

| 维度 | v5 headless + `--patch` | **v6 名册 + `delegate`** |
| --- | --- | --- |
| 按角色换模型 | ✅ | ✅ |
| 改模型要不要重启 | 不要 | **不要**（YAML 热生效） |
| 出现在侧边栏看板 | ❌ **独立进程，看板看不见** | ✅ **本会话子代理，看板可见** |
| 能否中途插话 / 看轨迹 | ❌ | ✅（`打开对话`） |
| 产物落盘 | 只能最后写，**超时=全丢** | 同左，但可用 `checkpoint` 模板规避 |
| 依赖 | 自造 `rb-run.mjs` + `route-*.yml`（8 个文件） | 一个插件 + 2 个 YAML |

**这就是「侧边栏什么都没有」的根因**：v5 派出去的是独立 headless 进程，**永远不可能出现在本会话的子代理看板里**。换名册后红蓝都是本会话子代理，看板与侧边栏立刻有东西。

**改模型（不用重启）**：

```powershell
# 改前先备份
Copy-Item <DSH_HOME>\subagents\rb-red.yaml <DSH_HOME>\subagents\_backups\rb-red.20261101-0412.yaml
# 改 provider / model 两行，保存即生效
```

**可用 provider**（desktop profile 已注册）：`longcat`、`spark`、`agent2api-trae`、`agent2api-workbuddy`。
> `spark` 需 `SPARK_API_KEY` 在 `.credentials.yaml` 的 `refs:` 下（已写）。

**v5 的 headless 方案保留为备用**：`node tools/rb-run.mjs <route> <任务包.md> <产物.md>`，用于「需要完全隔离、不在乎看板」的场景。路由文件仍在 `tools/route-*.yml`。

**成本原则（默认，不许破）**：

1. **日常只走 LongCat**（`rb-red` 默认 LongCat-2.5-Preview），不主动用按 token 计费的
2. 用户说「今天只有 X 能用」→ 改名册 YAML 两行，热生效
3. 同家族不同尺寸（lc25/lc20）算**弱跨模型**，`04` 必须写「同家族，独立性收益有限」
4. 跨厂商（LongCat ↔ Spark ↔ DeepSeek）算**强跨模型**，`04` 记「强独立性」
5. 路由调用失败 → 降级到池内下一条，**不自动改用付费模型**

**分配规则（主控执行，不问你）**：

1. **红队（技术审查员）** = 池里最强 → 默认 `rb-red`（LongCat-2.5）
2. **蓝队（修复）** = 池里另一个厂商 → 默认 `rb-blue`（Spark-x2.6）
3. **领域审稿人 / 魔鬼代言人** = 与红队不同优先
4. **复核红队** = 与 R1-a1 **同模型**（口径一致），但**必须是新实例**
5. 只有 1 条名册可用 → `04` 记「本轮同模型，独立性受限」

**硬要求**：`00-target.md` 记模型池；`04-summary.md` 的「主控决策」**逐角色记录实际 route**；出现降级要记原因。
**指纹校验（v3.3 简化）**：只在 **R1-d 收尾时校验一次**（基线 vs 交付件当前）。
> v3 的四个校验点实测 3 次运行**全部零命中**：红队改交付件这件事从未发生；而真实发生过的写事故是「迟到的红队覆盖了红队自己的产物」，已由 §2 的文件名隔离修复。中间三次校验是纯开销。

### 5.3 R2 / R3（复核 → 处置 → 复核 → 主控）

**产物编号规则（v3 明确）**：

- `01-cases.md`：**R1 建一次，之后只增不改**。新增用例以 `N01`、`N02`… 追加在表尾，并标"来源：R{n} 新增"。
- `02-blue.md`、`03-review.md`、`04-summary.md`：**每轮各自一份**，放在当轮目录，**不覆盖旧轮次**。

| 步 | 谁 | 输入 | 输出 |
| --- | --- | --- | --- |
| R2-a | 红队 `subagent` | 上一轮 `03-review.md` + 交付件当前版 | `03-review.md`（当轮）：逐条复核"已修是否真修" |
| R2-b | 蓝队 `subagent` | 当轮 03 + 未修清单 | `02-blue.md`（当轮）+ 交付件新版 |
| R2-c | 红队 `subagent`（新实例） | 当轮 02 + 交付件当前版 | `03-review.md` 追加"复核结论"节 |
| R2-d | 主控 | 全部 | `04-summary.md`（当轮）+ 闸门 |

**R2/R3 红队硬约束**：
- **不得重新造用例集**。
- 只复核三件事：① 蓝队"已修"是否真修（**重读文件 / 重跑命令**）；② 蓝队"不成立"的反证是否成立；③ 蓝队修改是否引入新问题（须给"前后对比 + 新行号"）。
- 允许的窄口（v3 新增，修缺陷 #6）：可补 **R1 未覆盖维度**的非回归缺陷，单轮 ≤3 条，必须写明"R1 为何漏"。

### 5.4 指纹校验（v3.3：四点降为一点）

单对话里文件系统共享，**无法区分"谁"改的**，只能按阶段归属。

v3 原本设四个校验点。实测 3 次运行（本机 2 次 + 外部独立复核 1 次）**全部零命中**——"红队改交付件"从未发生；而真实发生的写事故是「迟到的红队覆盖了红队自己的产物」，已由 §2 的文件名隔离修复。**中间三点是纯开销，且防的是一个从未发生的风险。**

**现行做法**：

| 时机 | 判定 |
| --- | --- |
| R1-d 收尾 | `node tools/redblue.mjs diff fingerprints/00-baseline.txt fingerprints/收尾.txt`；不等则列出被改文件，并要求与 `02-blue.md` 的"交付件改动"节**逐文件对应**；不对应 ⇒ 记"未申报改动"（严重） |

R2/R3 同样只在收尾校验。

## 6. 闸门

| 条件 | 结论 |
| --- | --- |
| 致命 = 0 且 严重 = 0 | **放行**（一般/优化进挂账表） |
| 仍有致命/严重 | 进下一轮 |
| 第 3 轮仍未放行 | **`GATE: BLOCKED`**，归档但**不得宣称定稿** |
| 未修编号集合与上一轮**完全相等** | 原地打转 ⇒ 直接 `GATE: BLOCKED`，不浪费下一轮 |

**口径定义（修缺陷 #4/#5）**：
- `未修 = 状态 ∈ {未修, 驳回, 部分修}`，按**编号集合**比较。
- **挂账不得包含红队判为「致命」或「严重」的条目**：那类必须"已修"或"不成立+反证"；判"挂账"即视为未修，直接进下一轮（修缺陷 #9）。
- 挂账条数 > 5 时在 04 记一条"挂账过多"提示，**不阻断放行**——闸门只认红队判定的致命/严重，挂账不改变判定级别。

> **v3.1 更正**：v3 初版写"挂账条数 > ceil(严重及以上条数 × 0.3) 即超限"。实测发现该公式在"零致命零严重"时上限为 0，会把 2 条优化级挂账误判成超限、逼出一轮无意义的 R2。已改为上面的"挂账不得含致命/严重"硬规则 + ">5 提示"软规则。

**放行必须写三样（缺一不算放行）**：致命/严重 0 的依据、未覆盖范围、挂账清单。

**外加「未决清单 + 最需人看的 3 条」（v3.3 新增）**：闸门仍自动判、不打断流程，但 04 必须列出**红蓝结论不一致**的条目，并按"若红队判对则影响多大"排序取前 3 条，逐条写清分歧点与双方证据。

> 理由：闸门没有外部真值，"致命=0 且严重=0 → 放行"本质是**形式合规**。人不可能逐条看，但看 3 条是成本最低的真实裁决点。这一步不阻断自动化，只是把裁决权留在可见的位置。

### 6.1 人类签字 `05-signoff.md`（v4 新增）

**问题**：零确认换来不打断，代价是**从头到尾没人看过**。对"打磨到极致"这个目标，人是唯一的外部真值。

**规则**：

- 闸门放行后，主控写 `04-summary.md` 的「最需人看的 3 条」，并生成 `05-signoff.md` 模板（待签）
- `05-signoff.md` 内容只有三样：**三条待确认项**（原样抄 04）、**每条的"确认/驳回"空位**、**签字行**
- **没有签字的 05，产物状态只能写「已放行（待签）」，不许写「定稿」**
- 人不必逐条审，只需看那 3 条，勾"确认"或写"驳回+理由"
- 驳回 ⇒ 进下一轮；确认 ⇒ 状态改「定稿」

**为什么不阻断流程**：签字是**异步**的。主控跑完就交，你什么时候有空什么时候签。不签字不阻塞下一轮，只阻塞"定稿"这个宣称。

**校验**：`redblue.mjs contract` 检查 `05-signoff.md` 是否存在；`04-summary.md` 的闸门节里若写「定稿」但没有已签的 05，报 `CONTRACT_VIOLATION: 定稿缺签字`。

## 7. 严重度判据（4 类，修缺陷 #7）

**分派算法**：先判"流程/规范失效"，再判"内容类型"。

1. 若交付件是**协议、规范、流程、模板、判据表** → 用 §7.4
2. 否则按内容：研究论文/报告 → §7.1；数据集/处理脚本 → §7.2；代码/工程 → §7.3
3. 两类都沾边 → 选覆盖面更严的一类，在 04 写明理由

### 7.1 研究论文 / 报告
| 级别 | 判据 |
| --- | --- |
| 致命 | 结论错误；数据造假或无法复现；核心公式/方法错误；署名问题 |
| 严重 | 关键论据缺失；不可复现；与文献矛盾无解释；统计不足以支撑结论 |
| 一般 | 表述含混、结构混乱、图表不可读、引用缺失 |
| 优化 | 措辞、排版 |

### 7.2 数据集 / 处理脚本
| 级别 | 判据 |
| --- | --- |
| 致命 | 数据本身错误；预处理导致结论反转；口径/单位错误 |
| 严重 | 缺失值处理不当；随机性未固定；缺种子或版本；抽样有偏 |
| 一般 | 命名、注释、日志 |
| 优化 | 性能、可读性 |

### 7.3 代码 / 工程
| 级别 | 判据 |
| --- | --- |
| 致命 | 丢数据/越权/安全漏洞 |
| 严重 | 边界未处理、资源泄漏、并发不安全、缺错误处理 |
| 一般 | 命名、结构、重复 |
| 优化 | 可读性、测试补充 |

### 7.4 协议 / 规范 / 流程（v3 新增）
| 级别 | 判据 |
| --- | --- |
| 致命 | 照它执行**必然**产出错误结论；或存在可静默放行致命缺陷的路径 |
| 严重 | 关键步骤不可执行（引用不存在的函数/字段/文件）；判据不可判定；自相矛盾到影响结论 |
| 一般 | 表述歧义、编号/命名不一致、缺执行锚点 |
| 优化 | 排版、冗余 |

### 7.5 软件项目（v4 新增）
| 级别 | 判据 |
| --- | --- |
| 致命 | 丢数据 / 越权 / 可被远程利用的漏洞 / 崩溃后不可恢复 |
| 严重 | 核心路径无测试；错误被静默吞掉；并发不安全；依赖有已知高危 CVE |
| 一般 | 耦合过高、大段重复、命名误导、缺 README/安装说明 |
| 优化 | 性能、日志、注释、可读性 |

**软件专属必查项**（技术审查员照单跑）：
1. 边界：空输入 / 超长输入 / 并发 / 权限不足 —— 每种都跑一次
2. 错误处理：抛异常的地方有没有人接
3. 依赖：`pip-audit` / `npm audit` / `osv-scanner` 至少跑一个
4. 测试：核心函数有没有测试；测试是否真断言了
5. 可复现：全新环境能不能装起来并跑通最小用例

### 7.6 竞赛题 / 评审制交付物（v4 新增）
| 级别 | 判据 |
| --- | --- |
| 致命 | 审题偏差（答的不是问的）；漏答某个子问；违反硬性格式直接判 DQ |
| 严重 | 子问回答不完整；评分点没覆盖；计算过程不可核 |
| 一般 | 排版 / 图表 / 引用不规范 |
| 优化 | 表述、篇幅利用 |

**竞赛专属必查项**：
1. **审题**：把题目每个问句拆出来，逐句问"我的答案里有没有直接回应"
2. **评分点**：拿到评分细则（能拿到时），逐条对照
3. **格式**：字数/页数/字体/文件格式/命名，逐项核
4. **可核性**：中间步骤是否写出来（评委要看过程分）

## 8. 证据纪律

- 引用必须指到：**文件 + 行号**，或**命令 + 可复现输出**，或**数据源位置**。
- **能复算就复算**：给命令、工作目录、实际输出片段。不能复算写明原因并标「未核实」。
- 禁止用"看起来合理""根据常识"当证据。
- 蓝队判"不成立"必须附反证（行号/命令输出/数据源三者之一）；**无反证一律计未修**。
- 无法核实的外部说法一律标「未核实」。

### 8.1 致命/严重必须可证伪（v3.3，替代"可复算覆盖率"）

原来的想法是"每条致命/严重必须绑定可执行验证"。这会把**只能靠判断的真问题**（论证逻辑断裂、伦理取向、写作质量）误伤掉。

改为按**可证伪**卡，三类任一即可立项：

| # | 形式 | 例子 |
| --- | --- | --- |
| ① | **命令复算** | 给命令 + 实际输出片段 |
| ② | **最小可运行反例** | 不需要原环境也能独立跑通的构造（如"全二次基对 RSS 与线性均值 R² 均为 1.0"） |
| ③ | **同文档内两个引用的直接矛盾** | 给出 A 行号与 B 行号，矛盾自明，读者一步可核 |

三类都不满足的，**只能立"一般（判断类）"**，不进闸门、进 §6 的"最需人看的 3 条"。

> 关键区分：**可证伪 ≠ 可执行**。逻辑断裂跑不出结果，但可以构造反例；只有"取向类"问题才真正无法证伪。

## 9. 用例数量与新增规则

- R1 红队用例 **≤ 20 条**，每条必须有**可判定的失败判据**与**触发输入**。
- 合并：仅当"维度 + 失败判据"语义完全相同才可合并，合并后保留被合并编号。
- 禁止拆分：合并后的用例不得在后续轮拆回。
- 新增（R2/R3）：见 §5.3 窄口，单轮 ≤3 条。

### 9.1 覆盖度：维度清单驱动（v3.3 新增）

**问题**：红队只造 20 条用例，若漏掉一整类问题（统计前提/伦理合规/引用完整性），闸门照样放行。而"未覆盖范围"过去是**主控写的**，等于没审。

**不能让红队自报覆盖**（自己评自己覆盖 = 无效）。改为：

1. 主控在 `00-target.md` 给**固定维度清单** = 六个通用维度 + 交付件类型专属维度（论文加"统计前提/引用完整性"；代码加"错误处理/资源"；数据加"口径/缺失值"）
2. 红队对**每个维度**必须填：`覆盖` / `不适用` / `未覆盖`，且填"覆盖"必须带 **≥1 个具体检查点指针**（哪条用例、哪个文件行）
3. 未覆盖项自动进 `04-summary.md` 的"未覆盖范围"

**防虚报的两道交叉**（缺一不可）：

- **蓝队反向申报**：蓝队额外填"我修的问题属于哪些维度"。红队说"伦理维度未覆盖"却修了伦理问题 ⇒ 虚报。
- **基准召回**（见 §9.2）。

### 9.2 基准召回：红队质量的可测量指标（v3.3 新增）

**问题**：红队把致命**漏判**成一般，现有机制发现不了（只有它误判成致命时，蓝队能反驳）。

**做法**：维护一个**历史已确认缺陷集**（每条：交付件、位置、缺陷、当时判定的级别）。每轮开跑时，把其中 1–2 条**以新缺陷的形式混回**给红队（"回顾式金丝雀"），看它能否独立重现。

- 命中 ⇒ 红队本轮质量可信
- 未命中 ⇒ 在 04 标「本轮红队质量存疑」，并把该轮结论降权（闸门结论不阻断，但必须写给用户看）

**低成本替代**（没建基准集时）：主控每轮**固定抽 3 条**红队判为"一般/优化"的，做定向复判，输出"维持/升级"。成本极低，能压住"漏判为低"的一侧。

### 9.3 错误类型目录（v4 新增，跨项目累积）

**问题**：机制不累积。第 2 轮不知道第 1 轮漏了什么；同一个错误类型会在不同轮次、不同交付件重复出现——实测课题16 的 C15 是"档位/量纲错"，蓝队修的时候**又犯了同类错**（N1）。

**做法**：所有缺陷必须归入下面的固定类型，不得自创（自创类型写在 `_redblue/error-types.md` 末尾，下一轮起生效）。

| 代码 | 类型 | 典型表现 |
| --- | --- | --- |
| E01 | 量纲/单位 | 把倍数标成 dB、场因子乘在功率域 |
| E02 | 口径不一致 | 同一量全文两套定义（9.9 dB vs 22.0 dB） |
| E03 | 引用归属错 | 句子记错文件/行号（v2:91 vs 02-blue:127） |
| E04 | 页码/条款错 | 引标准原文的 page/line 对不上 |
| E05 | 统计前提 | 样本不独立、无 CI、估计量选择无理由 |
| E06 | 逻辑断裂 | 论证链断、因果倒置、界向推错 |
| E07 | 覆盖遗漏 | 该做的实验/对比/声明没做 |
| E08 | 数据可复现 | 数字无法由原始数据重推 |
| E09 | 定义不一致 | 同一术语在两处的定义不同 |
| E10 | 结论强于证据 | "证明/必然"用于只是"提示/可能"的程度 |
| E11 | 实现缺陷 | 除零、零方差、边界未处理、未申报依赖 |
| E12 | 格式/合规 | 目标期刊或赛事的硬性格式要求不满足 |

**用法**：
1. 红队造用例时必须标 E 码
2. 04-summary 汇总"本轮各类型命中数"
3. 跨项目积累后，你就能看到"我这类错误最常犯哪一类"——**这才是真正的沉淀**
4. 基准召回（§9.2）直接从这里取样本

### 9.4 两阶段成本（v4 新增）

**问题**：18 条里最硬的 2–3 条贡献 80% 价值，但机制先造 20 条再筛，平均用力。

**做法**：

**与 §5.2 三角色的衔接（v4.1 澄清，原文自相矛盾）**：

| 阶段 | 技术审查员 | 领域审稿人 | 魔鬼代言人 |
| --- | --- | --- | --- |
| **阶段 1（探测）** | 只跑 3–5 条高价值点（清单见下） | **跑**（≤6 条，成本低） | **跑**（≤5 条，成本低） |
| 探测**有命中** | 展开全量（≤12 条，可派 2 实例取并集） | 已跑 | 已跑 |
| 探测**无命中** | **不展开**，记「探测未命中」 | 已跑 | 已跑 |

> **关键修正**：探测未命中时**仍然要跑领域审稿人和魔鬼代言人**。理由：这两个恰好是唯一能发现"方向错/不值得写"的角色，而"技术探测无命中"恰恰是这类问题最可能藏身的场景——技术全对但根本不该做。省它们等于省掉 V1 的全部价值。

**阶段 1 的高价值点清单**（按交付件类型预置）：

- **论文**：结论是否强于证据（E10）、数据是否可复现（E08）、引用是否可核（E03/E04）、统计前提（E05）
- **软件**：错误处理（E11）、依赖安全、测试覆盖、可维护性
- **竞赛**：审题偏差、子问覆盖（E07）、格式合规（E12）

**E 码归码责任（v4.1 补）**：红队自己标 E 码；**主控必须校验**——出现目录外的码，要么退回让红队改，要么由主控批准追加到 `error-types.md` 末尾（下一轮起生效）。**禁止静默自创**。

> 实测依据：课题15 的 18 条里，真正推翻论点的只有 C01/C02 两条；课题16 的 16 条里只有 C15/C01 两条。**先探测再展开**能省一半时间，且不降低命中率。

## 10. 产物与命名（修缺陷 #3/#8）

**短码唯一写法**：`{MMDD}{2位十六进制}`，如 `1031a3`。轮次目录 = `R{轮次}-{短码}`，如 `R1-1031a3`。

```
<产物根>/

├─ current.json             ← 当前轮次状态（可覆写）

## 11. 确定性工具（1 个 Node 文件，9 个子命令）

`node tools/redblue.mjs <子命令>`：

| 子命令 | 作用 |
| --- | --- |
| `init <roundDir> <交付件...>` | 建目录 + 写 `fingerprints/00-baseline.txt`（一次完成开工第 3、4 步） |
| `fp <outFile> <path...>` | 规范化指纹（小写哈希 + 两空格 + 绝对路径） |
| `diff <fpA> <fpB>` | 两快照比对，输出 `FP_MATCH` 或差异文件 |
| `shortcode <roundsRoot> <round>` | 短码 + 冲突 `-n` 递增 |
| `contract <roundDir>` | 产物契约校验（**R2 起豁免 `01-cases.md`**） |
| `audit <roundDir> [prevRound]` | 用例数审计（**认 `C` 与 `N` 两种编号**） |
| `recount <03-review.md>` | 统计复算（**前缀匹配级别**，只数逐条判定表） |
| `gate <03-review.md>` | 闸门机械判定：致命/严重 → 放行 / 进下一轮 |
| `validate <current.json\|state.md>` | 阶段/结论枚举校验 |
| `selftest` | 自检：5 组回归用例 |

**为什么换掉 bash（v3.3）**：

1. 目标机器（Windows）**没有 bash/awk/grep/sed，WSL 也未安装** → v3 的 8 个脚本一次都跑不起来。
2. mawk 在 C locale 下按**字节**匹配 `[（(]`，把「一般」(`e4 b8 80` **`e8 88`** `ac`)、「优化」(`e4` **`bc`** `98…`)、「已消除」(`e6 b6` **`88`**`…`) 从 0x88/0xbc 处截断 → recount 把三个级别词判成未识别。而「已消除」正是放行的主力。
3. Node 天然 UTF-8，一份实现跨平台，且能自带自检。

**两条硬要求**：

- **`recount` 每轮必跑**；与红队统计表不一致时**以脚本为准**并记挂账；`未识别 > 0` 时脚本 exit 1，不许静默通过。
- **`gate` 每轮必跑**；放行/进下一轮由它机械判定，**不靠模型数数**（实测红队的统计表和自己的逐条表就对不上）。

**脚本必须自带自检**：任何被赋予"以其输出为准"的脚本，若没有在样例上验证过，就不许上线。`selftest` 覆盖：级别解析（含 `致命 → 已消除`、`一般（残留）` 变体）、只数逐条判定表、`N` 系列计数、R1/R2 契约差异、闸门判定。

## 13. 已知限制（不装懂）

1. **同一个模型自己审自己**：红蓝同权重。这是天花板。想更强就把一方换成 `longcat_worker`（全新上下文 + 另一个模型）。
2. **弱独立**：主控把目标、验收标准、红队用例喂给下一方，世界观仍由同一模型框定。
3. **红队只读做不到硬隔离**：只能靠 §5.4 收尾校验一次；且分不清"谁"改的，只能按阶段归属。**实测该风险 3 次运行零发生**，所以不再为它付四点校验的成本。
4. **闸门没有外部真值**：致命/严重是模型贴的标签；零确认意味着没人复核。这是换取"不中断"的取舍。
5. **文件契约没有强制力**：跳过步骤不会被拦住，只能靠 `contract` 事后查。
6. **闸门本质是形式合规**（v3.3 承认）：判 0 不等于没问题。唯一缓解是 §6 的"最需人看的 3 条"——把裁决权留在人看得见的地方，而不是替人判。
7. **红蓝的动机偏差方向相反，只压得住一侧**：红队倾向**过度升级**（多抓显得有价值），蓝队倾向**过度降级**（少修省事）。所以"红判高"会被蓝队压住，"红判低"压不住——靠 §9.2 基准召回 / 抽检补。
8. **R2/R3 从未真跑过**：两次实跑都在 R1 就放行或作废，收敛性未验证。故 v3.3 把 R2/R3 降为**可选**（最小有效核 = 造 → 修 → 实跑复核）。

> **U4 已解决（2026-11-01 主控亲眼确认）**：GUI 认证走**签名 cookie**，不是 `?token=`。

> 但签名密钥是 `$DSH_HOME/.credentials.yaml` 里 `client-connection/browser-session` 的 grant，
> 可以离线自签：`HMAC-SHA256(secret, body)`，cookie 名 `dsh-auth-` + `base64url(sha256(authority))`，
> 值 `v1.<base64url(payload)>.<base64url(sig)>`，payload 需含 `version/authority/issuedAt/expiresAt`。
> 实测 `GET /` → **200**，页面标题 `DeepSeek Harness`，侧边栏与看板均正常渲染。

### 14.4 v6.2：从外部技能吸收的四点（2026-11-01）

## 15. v6.3：R5 实测（零上下文红队 + 实际运行工具）

### 15.1 最关键的机器证据

```

R1-skill-audit    0    0    0     22   29
R2-skill-audit    0    0    0     27   29
R3-skill-audit    0    0    0     29   29      ← 三轮"完美收敛"

### 15.5 新的强制规则：先冻结哈希再动手

R5 的两个红队实例钉的是**不同快照**：

| --- | --- | --- |
| 第一实例 | `2D08094C374E` | 58684 |

### 15.7 元教训（写进 SKILL.md §8）

1. **解析器的失效方向永远是「少算」，不是「报错」。** 每次缺陷的表现都是 `致命=0 严重=0`——一份实际含致命/严重的文件被读成干净。这比「0 行」更危险，因为它看起来像成功。
2. **「级别」和「状态」是两个独立维度。** 状态说明「修没修」，级别说明「有多严重」。合并 = 严重度被处置进度掩盖。
3. **同一批数据，两个命令不许给出相反结论。** 如果给了，一定是其中一个没有复用另一个的判据。
4. **被审对象在审计期间被改写 = 审计结论无锚点。** 必须先冻结哈希。
5. **红队的价值来自「实际运行」，不来自「读文档」。** 前四轮 0 致命与 R5 的 2 致命，差距就在这里。
