# R5 总结：第一次真正跑通「零上下文红队 + 实际运行工具」

## 一句话结论

**R5 是本机制的转折点。** 前四轮都是「读文档提意见」，R5 第一次让红队**自己造探测件、自己跑工具、自己看退出码**——结果抓到 **2 条致命缺陷**，而这两条是 R1–R4 四轮文档审阅完全没发现的。

## 最关键的一张表

```
轮次             致命 严重 一般 已消除 合计
R1-skill-audit    0    0    0     22   29
R2-skill-audit    0    0    0     27   29
R3-skill-audit    0    0    0     29   29      ← 三轮"完美收敛"
R5-skill-audit    0    2    2     13   17      ← 换独立红队，立刻现形
```

**R1–R3 连续三轮 `致命=0 严重=0`，看起来已经收敛。R5 一进来，`严重=2`，连续干净轮数从 3 掉到 0。**

这就是「自己审自己越审越松」的机器证据。不是假说，是 `converge` 命令的输出。

## 本轮抓到的 2 条致命

### 致命 1：级别列被状态列整个吞掉（红队第一实例 N05）

旧格式 `| 编号 | 级别 | 状态 |` 里，状态词（已修/未修）决定分桶，**级别列被丢弃**：

| 输入 | 旧输出 | 真相 |
| --- | --- | --- |
| 10 行 `\| C01 \| 致命 \| 未修 \|` | `致命=0 严重=0 挂账=10` | 10 条致命，一条没修 |
| 10 行 `\| C01 \| 致命 \| 已修 \|` | `致命=0 已消除=10` | 10 条致命，已修好 |

**无论修没修，「致命」都被清零。** 闸门靠兜底扫描才勉强拦住，而且只抓到 1/10。

**修法**：状态列决定桶、级别列另存 `claimedLevel`；`recount` 额外打印「未结案的真实严重度」，`gate` 对两个来源取大值。实测现为 `致命=10`。

### 致命 2：两个命令对同一批数据结论相反（红队第二实例 S02）

```
reattack R2-convA R2-convB  →  REATTACK: FAIL (false_fix_detected)   exit 1
converge --n=2              →  CONVERGE: PASS (converged)           exit 0
```

`converge` 文档列了 4 条收敛条件，实现只查 3 个变量，**从不调用 `cmdReattack`**。于是「上一轮声称已修、这一轮又被打开」这件事，`reattack` 看得见、`converge` 看不见。

**修法**：`converge` 加条件 2b 假修复检测。现输出 `CONVERGE: NOT_YET (上一轮声称已修的被重新打开（假修复）)` exit 1，与 `reattack` 一致。

## 红队是怎么做到的（方法学价值）

红队没有「读文档、提意见」，而是：

1. **钉住快照**：先把 `SKILL.md` 和 `redblue.mjs` 复制成 `_probe/SKILL-pin-R5.md`、`_probe/rb-pin-R5.mjs`
2. **造探测件**：写了 20 个针对性 fixture（`e1-num-ids.md`、`e11-dashed-id.md`、`e12-empty-review.md`、`n05-fatal-unfixed.md` …）
3. **实际运行**：`D:\node.exe <钉住副本> recount <fixture>`，看退出码
4. **看差异**：预期 `致命=1`，实际 `致命=0 exit 0` → 缺陷

**这个方法是本机制可信度的唯一来源。** 前四轮之所以越审越松，就是因为没有这一步。

## 3 条已知限制（未修，留给 R6）

1. **`bundle` 只核「文件在 + 行号 ≤ 行数」，不核该行内容。** 造一份 5 行文件、第 5 行随便写，复核件声称该行写着某段话 → `BUNDLE: OK` exit 0；同一引用换 `cite` 带引文则 `CITE_FAIL` exit 1。**行号检查对内容真假零分辨力。** 要真修必须强制每条引用带引文，会改动全部历史格式。
2. **`contract` 不核语义**：`GATE: PASS` 不在末行仍 `CONTRACT_OK`。
3. **`audit` 对历史轮次全判无效**：四个轮次全部 `ROUND INVALID` exit 2。这是 bundle 先失败的设计后果，但缺一条「历史轮次因文件被删而不可复算」的显式提示。

## 本轮暴露的最严重的方法学问题

**两个红队实例钉的是不同快照。**

| 实例 | `redblue.mjs` 哈希 | 字节 |
| --- | --- | --- |
| 第一实例 | `2D08094C374E` | 58684 |
| 第二实例 | `0EDDB234BAF4` | 63193 |
| 最终 | `820511CEAD33C8D7` | 77271 |

被审对象在审计期间被改写 **8 次**（48791 → 77271 B）。两个红队看到的不同工具，相差 4509 B。

**第二实例明确提出：「主控先冻结哈希，再让红蓝双方复算；否则任何『已修/未修』结论都只对某个瞬时快照成立。」**

这条建议已被采纳：`00-frozen.txt` 已冻结本轮最终快照，R6 起必须先冻结再动手。

## 元教训（写进 SKILL.md §8）

1. **解析器的失效方向永远是「少算」，不是「报错」。** 每一次缺陷的表现都是 `致命=0 严重=0`——一份实际含致命/严重的文件被读成干净。这个方向比「0 行」更危险，因为它看起来像成功。
2. **「级别」和「状态」是两个独立维度，不能用一个列代替另一个。** 状态说明「修没修」，级别说明「有多严重」。合并 = 严重度被处置进度掩盖。
3. **同一批数据，两个命令不许给出相反结论。** 如果给了，一定是其中一个没有复用另一个的判据。收敛的定义里必须包含「上轮声称修好的，本轮没被重新打开」。
4. **被审对象在审计期间被改写 = 审计结论无锚点。** 必须在动手前冻结哈希。
5. **红队的价值来自「实际运行」，不来自「读文档」。** 前四轮的 0 致命与 R5 的 2 致命，差距就在这里。
